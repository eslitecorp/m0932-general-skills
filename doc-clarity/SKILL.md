# Doc Clarity — 文件品質與可讀性審核

核心理念：**文件是給「特定讀者」做決策用的，不是作者的工作筆記。先確認「目的 × 對象」,再談範圍與結構;文字貼近該對象、精簡到剛好夠用。用詞要精確:刪形容詞、定義先行、能刪則刪 —— 字多不等於清楚,常是相反。**

適用對象：任何文件——技術文件（探勘分析、架構/設計文件、migration 分析、research 報告、實作計畫）、提案與簽核、公告與政策、會議記錄、對外說明。原則與文件主題無關，審核時一律引用原則編號，不假設文件領域。

> 本 skill 為 MVP（v0.13）。應用到新文件型態時發現的強化點，更新原則表並記錄於文末版本紀錄。

---

## 模式判斷

| 使用者意圖 | 模式 |
|-----------|------|
| 提供現有文件，要求審核/評估可讀性 | **審核模式** |
| 描述要寫的文件，詢問結構/方向 | **建議模式** |
| 提供文件並要求「直接改」 | 審核模式 → 問題清單經確認後執行改寫 |

## 審核流程：三遍掃描

不論文件大小都走三遍，確保大文件（數千行、多份附件）也能維持全局觀，避免逐段點評。

### Pass 1 — 建立文件地圖
逐章記錄（文件超過 ~800 行時分段讀取，邊讀邊記，不要等全部讀完）：

- **目的與對象(先判)**：這份文件的單一目的?主要對象是誰?每章實際在對「哪種讀者」說話（供 Pass 3 查混雜對象/過長）
- **大綱**：每章一句話「這章存在的目的」
- **術語清單**：每個系統/概念出現過的所有稱呼與寫法（供 Pass 3 查混用）
- **資訊重複註記**：同一資訊出現在哪幾處
- **容器既有內容（只有追加式產出需要）**：若這份產出要追加進一個已經有內容的地方（issue／MR 留言、
  追加型文件、討論串），先讀完容器裡的既有內容，列出「已經說過什麼」。這份清單供 Pass 2 的 1-6 用

### Pass 2 — 依支柱逐章審核
對照五大支柱原則表（支柱零先判），逐章記錄 finding：`章節 / 原則編號 / 嚴重度 / 一句話描述 + 改法`。只依賴文件地圖 + 當前章節內容判斷，不需要全文在手。

### Pass 3 — 全局綜合
- **用目的/對象記錄檢查混雜對象與過長（0-1、0-3、0-5）**：一份文件是否服務多種讀者?該拆嗎?
- **主題與閱讀時間（0-7、0-8）**：文件是否概觀與細節混寫?單一主題嗎?主要對象 5–10 分鐘讀得完嗎?超時 → 建議拆成「概觀 + 逐主題/scope」多份
- **比喻/口號掃描（3-12）**：全文(含標題、章節名)有無高大上卻不精準的比喻;有 → 換本名
- 用術語清單檢查全文一致性（3-1、3-5）
- 用重複註記檢查合併機會（2-2）;**多份文件時,同一張表/清單/事實只在一份維護(single source of truth),他處連結引用,不各自複製一份**;**交叉連結逐條核對:連結文字＝目標文件標題**
- 合併重複 finding、按嚴重度排序、產出報告
- **多份文件時,附一句結構建議**：概觀文件放什麼、各細節文件各扣哪個主題、彼此如何互引

## 五大支柱(支柱零最優先)

### 支柱零：目的與對象 — 先確認為誰而寫、為何而寫

| # | 原則 |
|---|------|
| 0-1 | **一份文件一個主要對象**：先定 primary audience（主管 / RD / QA / PD / 跨部門 …）。對象決定用詞、深度、篇幅 |
| 0-2 | **開頭明示「目的 + 對象 + 一句話結論」**：讀者 3 秒判斷該不該讀、是不是給他看的 |
| 0-3 | **兩個對象就拆**：同一文件同時服務兩種讀者（如主管要「決策/指標」、同仁要「事項/DoD」）→ 拆成兩份,或明確分區並各自精簡;不要讓一方讀另一方的內容 |
| 0-4 | **語言貼近對象**：對非工程角色去術語、講白話與影響;對工程角色才用技術詞。表頭/用語隨對象切換（呼應 3-3） |
| 0-5 | **精簡到對象所需**：只留該對象「做決策 / 行動」需要的;其餘導向 single source of truth（呼應 1-4）。**長度是症狀,對象不清是病根** |
| 0-6 | **作者也是對象**：寫完自己讀一遍;若連自己都難快速消化,就是差勁的文件,別交出去 |
| 0-7 | **概觀先於細節,一份文件一個主題**：多 scope / 多階段 / 多主題的工作,先寫一份**概觀文件**——全貌、路線圖、各文件入口;再讓每個 scope / 主題各自一份**細節文件**。每份文件扣住**單一主題**,只放服務該主題的內容;與主題無關的(別的 scope、別的階段、旁支細節)移到對應文件或刪,不塞進同一份。判斷法:一份文件若同時講「整體全貌」又講「某一步的實作細節」,就是概觀與細節混寫 → 拆 |
| 0-8 | **閱讀時間預算 5–10 分鐘**：一份文件的初步目標是主要對象 5–10 分鐘讀完。超時**先問「是不是主題太多」**(套 0-3 / 0-5 / 0-7 拆分),而不是壓縮字級或砍必要說明。長度是症狀,主題過載與對象不清才是病根 |

> 判斷法：讀完問「這份是給誰、幫他決定/做什麼?」答不出單一對象與單一目的 → 先套支柱零,再談其餘。

### 支柱一：範圍紀律 — 文件只承載它該回答的問題

| # | 原則 |
|---|------|
| 1-1 | **開頭明示目標與非目標**：這份文件要回答哪 1–3 個問題；明確不處理什麼（Google Design Doc 的 Goals / Non-Goals） |
| 1-2 | **超出範圍的內容整段移除**：標註「未涵蓋」「待確認」但不是待討論議題的段落，刪除 |
| 1-3 | **已有結論的議題不留分析過程**：只留一句結論；文件保留的開放議題應全部是「仍需討論」 |
| 1-4 | **細節導向 single source of truth**：已有權威文件（spec、guide）涵蓋的細節，只留概覽 + 連結 |
| 1-5 | **只列差異，不列未變更事項**：對照類內容只呈現有變化的項目 |
| 1-6 | **追加式產出只寫增量**：往已經有內容的容器新增時（issue／MR 留言、追加型文件、討論串），只寫容器裡還沒有的。與前兩條的分界——1-4 管「細節導向外部正本」，1-5 管「同一份產出內部的對照只列變化」，1-6 管「這份產出相對於**容器既有內容**的增量」。判準是「收件人還缺什麼」，而收件人已知的來源包含同一容器裡前面幾則 |

### 支柱二：結構與密度 — 每個段落、表格、圖都有不可替代的資訊量

| # | 原則 |
|---|------|
| 2-1 | **結論先行、見林到見樹**：全文與每章都「最重要的放最前面」—— 讀者注意力最高時先給結論/全貌,再逐層展開細節（Minto Pyramid / BLUF）。開頭 30 秒能吸收的,決定整份文件的價值 |
| 2-2 | **同一件事只說一次**：多處描述同一組事實 → 合併;若反覆出現且份量夠,抽成**獨立 topic/章節**,他處只引用連結,不重述 |
| 2-3 | **對應到相同目標的列合併**：多對一的映射收成一列 |
| 2-4 | **按維度拆表**：一張表混雜多種性質的資訊時，拆成多張，每張只講一個維度 |
| 2-5 | **流程沒變就不畫細節圖**：只是實作替換而流程不變時，刪 sequence diagram，留概覽表 |
| 2-6 | **風險/議題表只留真正未解的項目**：已解決、已就緒的移除 |
| 2-7 | **選對呈現形式**（見下表）：同一資訊只用一種形式呈現一次 |
| 2-8 | **mermaid 只用在合適情境，單張圖只講一件事**（見下表） |

呈現形式選擇：

| 內容性質 | 建議形式 | 不適合時的替代 |
|---------|---------|-------------|
| 對照、枚舉、屬性清單 | 表格 | — |
| 跨系統訊息往返、時序 | mermaid `sequenceDiagram` | 步驟只有單向 → 有序清單 |
| 架構拓撲、資料流向 | mermaid `flowchart LR` | 節點 ≤ 3 → 一句話描述 |
| 循序 guard clause（主路徑橫向、錯誤向下） | mermaid `flowchart LR` | 無分支 → 有序清單 |
| 複雜條件樹（多層巢狀） | mermaid `flowchart TD` | 層數 > 3 → 拆成多張 |
| 狀態轉換 | mermaid `stateDiagram-v2` | — |
| 因果、論證、取捨 | 短段落文字 | — |
| 前後變化 | Before / After 對照表 | — |

mermaid 紀律：
- 合適情境：關係或順序比文字更直覺（多系統互動、條件分支、狀態轉換）
- 單張圖的節點 ≤ 7；sequence 的 message ≤ 6；超過則拆圖
- 一張圖只講一件事；不用一張圖覆蓋整個流程

### 支柱三：表達一致性 — 段落相互銜接，全文一個聲音

| # | 原則 |
|---|------|
| 3-1 | **術語統一**：同一系統/概念全文只用一種稱呼；大小寫、中英文一致 |
| 3-2 | **段落銜接**：後段沿用前段建立的術語與維度框架，不另起爐灶 |
| 3-3 | **表頭語言不混雜**：同一張表的欄位標題要嘛全技術用語、要嘛全白話 |
| 3-4 | **互動描述主詞明確**：欄位/句子結構呈現「誰透過什麼方式對誰做什麼」 |
| 3-5 | **表示法統一**：箭頭、空格、括號、代碼標記等記號全文一致 |
| 3-6 | **版本更新紀錄**：文件有版本表（版本/日期/變更摘要），修訂時同步更新 |
| 3-7 | **逐詞自問,不靠黑名單**:對每個「感覺對但說不清」的修飾詞/抽象詞反問四題 ——(1) 為什麼用這個詞?(2) 具體用意是什麼?(3) 有沒有更精確的描述?(4) 這個詞的字面意思,讀者不看你的解釋能不能推出你的用意?答不出用意 → 換成事實/數字或刪;答得出用意但字面推不出來(如自造的「-化 / -性 / -機制」) → 換成推得出來的詞。**是逐詞質疑,不是背禁用詞表**;窮舉會漏,質疑不會 |
| 3-8 | **定義先行**：專有名詞、縮寫、自造詞,首次出現即一句定義;不假設讀者已知。缺定義的詞是誤解來源 |
| 3-9 | **一句一意、能刪則刪 —— 但簡明 ≠ 模糊**：長句拆短、一句一意;刪掉不損意的字。**但精簡的前提是語意仍清楚**:若刪字後讀者看不出「檢查什麼 / 誰對誰 / 到什麼程度」,寧可多幾個字補精確。**精確優先於字數**;省字省到看不懂,是更差的文件 |
| 3-10 | **抽象詞落地(3-7 的落地工具)**:詞通不過 3-7 自問時,補「主詞 → 動作 → 受詞 → 可驗證標準」。補得出就改寫,補不出 = 還沒想清楚,別交出去 |
| 3-11 | **句意分類**：每句分清是 **為什麼(why) / 做什麼(what) / 如何做(how)**,以及 **行動 vs 定義**;類型混在一句 → 拆開。讀者才知道這句要他理解、還是要他做 |
| 3-12 | **忌比喻與口號,概念用本名**:不用「北極星 / 踏腳石 / 建樹建林 / 這道縫 / 護城河 / 賦能 / 打通任督二脈」這類**讀來高大上、指涉卻不精準**的比喻與口號。它們讓讀者要再翻譯一層才懂,且常掩蓋「其實還沒想清楚具體是什麼」。改用**本名**:北極星→終態目標、踏腳石→階段/前置工作、建林建樹→概觀/細節文件、這道縫→(直接講那個機制,如「唯一入口」)。判斷法:把詞換成字面直述後若資訊沒少,原詞就是裝飾 → 換掉。**這條連文件標題、章節名、principle 命名都適用**——標籤也不該用比喻 |

### 支柱四:讀者知識落差 — 作者手上有、讀者手上沒有的,要補進文件

支柱一到三全部通過的文件,仍然可能讓讀者看不懂:作者知道那個表長什麼樣、知道那段程式碼在做什麼,所以自己讀不出問題(0-6 的自我消化測試擋不住這種)。

判斷法(統一自問):**逐個指涉問「讀者是從哪裡知道這個的?」答案若是「從程式碼裡 / 從我腦裡 / 從另一份他沒讀的文件」→ 補一句,或刪掉這個指涉。**

方法同 3-7 ——**不背「哪些形態要補」,逐個指涉質疑**。以下六條是常見形態,**是示例不是窮舉**;遇到沒列到的形態,回到上面那句自問。

| # | 原則 |
|---|------|
| 4-1 | **指示詞要指名**:「上面那套流程」「前述機制」「這個做法」跨段落回指時一律寫出名稱。自問:讀者要往回翻幾段才對得上? |
| 4-2 | **識別符要附身分**:表名、欄位、型別、函式、套件路徑首次出現時,一句話說明它是**什麼種類**(表?JSONB 欄位?策略介面?)與承載什麼。只給名字＝只有作者讀得懂。自問:讀者不開程式碼,知道這是什麼嗎? |
| 4-3 | **用領域語言解釋,識別符只作對照**:主要敘述用業務概念(門檻、折抵、適用範圍),程式識別符放括號或對照欄,不當主詞。**貼原始碼片段不算解釋**。自問:把識別符全遮掉,這句話還說得完整嗎? |
| 4-4 | **規則要附一個數值範例**:挑選規則、計算順序、捨去行為,給一組「輸入 → 輸出」的具體數字。自問:讀者能不能照文件自己算出一個例子來驗證? |
| 4-5 | **未介紹的替代方案不當對照**:寫「採 A 而非 B」時,B 必須是讀者認得的、或你會順便解釋的;否則刪掉 B,只寫 A 與理由。自問:讀者認得 B 嗎?不認得,這個對照就只增加負擔 |
| 4-6 | **引用既有元件要標示前置知識**:沿用/參考既有實作時,明說讀者需不需要先懂它 —— 需要 → 給連結與一句摘要;不需要 → 直接寫「不需先了解,只需知道它提供 X」。自問:讀者會不會為了讀這段先去翻程式碼? |

> 與 3-8 的分界:**3-8 管「詞」**——讀者不知道這個詞是什麼意思;**支柱四管「詞以外的指涉物」**——讀者不知道這個東西在哪、長什麼樣、要不要先去看。詞彙落差見 3-8,本支柱不重述。
>
> 邊界:本支柱判斷「這句話讀者看不看得懂」,不判斷「這個結論對不對」。無依據的比較級(「更好」「不足以抵銷」)屬設計判斷,交給 code review,不在此列。

## 審核模式輸出

```markdown
## 文件品質審核：<文件名>

### 目的與對象(先答)
- 目的:<單一目的> ｜ 主要對象:<單一對象> ｜ 是否混雜對象/該拆:<是/否 + 說明>

### 總評
🟢 良好 / 🟡 需改善 / 🔴 需大幅重構 — 一句話（含「對象是否清楚、篇幅是否過長」)

### 問題清單（依支柱分組;支柱零優先）
- 🔴 [0-3] <章節>：<問題> → <改法>
- 🔴 [1-3] <章節>：<問題> → <改法>
- ⚠️ [3-1] <章節>：<問題> → <改法>

### 優點
- ✅ <值得保留的部分，避免改寫時誤刪>

### 建議改寫順序
0. **對象（先定位/拆分）** 1. 範圍（刪） 4. 落差（補） 2. 結構（併） 3. 表達（修）
```

嚴重度：🔴 讀者會誤解或找不到重點 / ⚠️ 增加閱讀成本。

## 建議模式輸出

依文件類型套用對應骨架，再以五大支柱客製：

| 文件類型 | 參考骨架 |
|---------|---------|
| 探勘/影響分析 | 背景與目標 → 整體變化（Before/After）→ 影響範圍 → 差異細節 → 準備事項 → 風險與開放議題 |
| 設計文件 | Context → Goals / Non-Goals → Design → Alternatives Considered → 風險（Google Design Doc） |
| 決策紀錄 | Context → Decision → Consequences（ADR） |
| 問題解決／流程改善 | 背景 → 現況 → 目標 → 根因 → 對策 → 追蹤（A3）。與「探勘/影響分析」的分界：那份回答「這次變更影響到誰」，這份回答「這個反覆發生的問題根因是什麼」 |
| 事後回顧 | 預期 → 實際 → 落差原因 → 下次做法（AAR）。用於結案、事故檢討；只在事實已經收斂後寫 |
| 升級／求援／交接訊息 | 現況 → 背景 → 評估 → 建議（SBAR）。訊息而非文件，四段各 1–2 句；對上溝通時已決定的事直接宣告，只對開放項目徵詢 |
| 說明性文件 | 依讀者目的選 Tutorial / How-to / Reference / Explanation，不混寫（Diátaxis） |
| 提案／簽核 | 要批准什麼 → 為什麼現在 → 選項與取捨 → 成本與影響 → 需要對方做的決定。結論一句話放最前（2-1）；對象是有權核准的人，不是執行的人 |
| 公告／政策宣達 | 適用範圍 → 生效時間 → 要做什麼 → 例外與問題反映管道。對象是被規範的人；核准過程與制定理由不進正文 |
| 會議記錄 | 決議 → 待辦（負責人＋期限）→ 未決議題 → 背景。決議先行，逐字發言不進正文（呼應 1-3） |
| 對外說明 | 發生什麼 → 對你的影響 → 已經做了什麼 → 需要你做什麼 → 下次更新時間。全程去內部術語與內部代號（0-4、4-2） |
| 多 scope / 階段工程 | 概觀（README：全貌+路線圖+各文件入口）+ 逐 scope 文件（各扣單一主題）+ Reference（查閱用）+ 決策/待確認（跨 scope）。每份 5–10 分鐘可讀（0-7、0-8） |

輸出內容：

```markdown
## 文件撰寫建議：<主題>

### 目的與對象（先定）：單一目的 + 主要對象 + 用詞深度;若有兩種對象 → 建議拆成幾份、各給誰
### 這份文件要回答的問題（1–3 個）
### 建議結構（每章一句話：承載什麼、為什麼需要、對誰）
### 範圍邊界（寫入 / 導向外部 + single source of truth / 不寫）
### 術語表（開頭先定義全文統一的稱呼與表示法;依對象決定要不要去術語）
```

## 執行注意事項

1. 嚴格按三遍掃描執行，finding 隨讀隨記。
2. 每個問題標注原則編號，可追溯方法論依據。
3. 改寫前先列問題清單給使用者確認，不直接重寫整份文件。
4. 改寫時同步更新文件版本紀錄（3-6）。
5. Markdown linter 的表格對齊類警告（如 MD060）不影響渲染，不列入問題清單。
6. **審查問答的答案要回寫文件**:回覆審查意見時補出來的資訊,若是文件本身缺的,寫進文件,不是只回在留言串裡。留言回答了不等於文件表達了。
