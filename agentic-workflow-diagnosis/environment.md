# 第二層：環境診斷

**判斷依據**：`behavior.md` 的行為調整已實施**並複測**，資源壓力仍在，才進本層。

> ## 平台範圍：macOS

## 量測程序

### 系統層（每個採樣時點都跑）

```bash
./scripts/probe_host.sh          # 以上全部＋設定層檢查，一次跑完
```

或逐項手動取：

```bash
vm_stat                          # Pages stored in compressor / Compressor / Pageouts / Swapouts
sysctl -n vm.swapusage           # swap 已用 / 上限
memory_pressure                  # 系統自報的記憶體可用百分比（必取）
uptime                           # load average
sysctl -n hw.ncpu hw.memsize     # 核心數、實體記憶體（換算比值用）
```

換算成無因次比值後才進判準，**不要直接比 GB** —— 不同角色負載差異大，比值才能跨機器對照：

| 符號 | 定義 | 注意 |
|---|---|---|
| `ρ` | compressor 邏輯量 / compressor 實體佔用 | — |
| `σ` | swap 已用 / swap 上限 | **上限為 0 時是 UNDEFINED，不是 0**（見下） |
| `λ` | load average / 核心數 | — |
| `φ` | free / 實體容量 | 與 `memory_pressure` 並看，兩者語意不同 |

### `σ` 在 swap 未配置的機器上是 UNDEFINED

⛔ **不得把 `0/0` 寫成 `σ = 0`。**
〔事證：某機 `sysctl -n vm.swapusage` 的 total 是 `0.00M` —— swap 根本沒配置。
`σ = 0` 與「swap 有配置但完全沒用」在數值上一樣，在意義上完全不同〕

**改以 `Swapouts` 為主判據**：它自開機起單調遞增，直接回答
「這台機器的記憶體壓力洩壓閥開過沒有」，比瞬時的 `σ` 乾淨且不會 undefined。
`Swapouts = 0` 且 uptime 夠長 → 這台從來沒有被逼到要換出。

`memory_pressure` 的自報值列入**必取**：它是系統自己的判斷，
比從 `vm_stat` 推的 `φ` 更不容易誤讀（`φ` 低但系統說壓力不大是常態，多為快取）。

### Process 層 — 四個取數陷阱

**陷阱一：RSS 在高記憶體壓力下嚴重低估。**

- ⛔ **不得以 `ps -o rss` 作為佔用依據，一律取 `phys_footprint`**
  〔事證：實測某 process RSS 2.6 MB vs phys_footprint 30 MB，**差 11.5 倍** ——
  不是它小，是它整個被換出去了〕

```bash
vmmap --summary <pid> 2>/dev/null | awk -F: '/Physical footprint:/{gsub(/ /,"",$2); print $2}'
```

**陷阱二：`ps` 在記憶體壓力下回傳截斷結果。**

- ⛔ **不得以單次 `ps` 的輸出當 process 清單，用 `pgrep` 逐一列舉**
  〔事證：該機 `ps` 只列得出 31 個 process，`pgrep` 顯示實際 700+〕
- **`ps` 與 `pgrep` 計數不一致這件事本身就是壓力證據**，要記進失敗台帳

```bash
pgrep -f '<pattern>' | while read -r p; do
  printf '%s\t%s\t%s\n' "$p" "$(ps -o comm= -p "$p")" \
    "$(vmmap --summary "$p" 2>/dev/null | awk -F: '/Physical footprint:/{gsub(/ /,"",$2); print $2}')"
done
```

**陷阱三：footprint 加總會因共享頁重複計算而高估。**

天花板校驗，超過即該次量測作廢重取：

```text
Σ(各項 footprint) ≤ 實體記憶體 + compressor 邏輯量 + swap 已用
```

**陷阱四：查數工具的旗標在不同平台語意不同，失敗時可能靜默回 0。**

- ⛔ **macOS 的 `pgrep` 不支援 `-c`**。`pgrep -fc <pattern>` 會印 usage 到 stderr 並回傳 0，
  若把 stderr 丟掉或只取 stdout，會讀成「找到 0 個 process」
  〔事證：據此誤判「沒有任何活著的 client」，進而把 12 個使用中的容器判成孤兒〕
- **計數一律用 `pgrep -f <pattern> | wc -l`**，並在關鍵判斷前用第二種方式交叉驗證
  （例如逐一 `ps -o command= -p <pid>` 印出來看）

> 一般化：**做刪除動作之前，先用第二種方法確認要刪的東西真的是可刪的。**
> 這條在本層特別重要 —— 第二層的動作多半是不可逆的清除。

**陷阱五：`ps -o pcpu` 是 process 生命期平均，不是瞬時值。**

- ⛔ **A/B 型的 CPU 量測不得用 `ps -o pcpu`，一律用 `top -l 2` 取第二次採樣**
  〔事證：對一個已跑 21 天的 process 做「閒置 vs 大量檔案 I/O」A/B，
  `ps` 給出 A=204.7%／B=201.2% —— 看起來「沒差」，那是 21 天平均把差異稀釋掉的**偽陰性**；
  同一時段 `top -l 2` 給出 A=246.1%／B=271.2%，差異真實存在〕

```bash
top -l 2 -o cpu -n 8 -stats pid,cpu,mem,command | awk '/^PID/{n++} n==2'
```

第一次採樣沒有前一次可比，數字不可信；**一定要取第二次**。

**陷阱六：受保護的 process 連 footprint 都拿不到。**

- ⛔ **`vmmap` 失敗時不得跳過該 process**（那通常正是最大的消耗者），
  改用 RSS 並**明確標為下界**，不得與其他項的 `phys_footprint` 混在同一欄相加
  〔事證：某機最大的單一消耗者是資安代理，`vmmap --summary` 對它回傳空字串（受系統保護），
  只剩 `ps -o rss` 的 1,395 MB —— 而依陷阱一，RSS 在高壓下嚴重低估，
  所以真實值只知道「不小於 1,395 MB」〕

```bash
fp=$(vmmap --summary "$pid" 2>/dev/null | awk -F: '/Physical footprint:/{gsub(/ /,"",$2); print $2}')
[ -z "$fp" ] && fp="UNKNOWN（受保護，RSS 下界 $(ps -o rss= -p "$pid") KB）"
```

> 陷阱四、五、六是同一種病的三個變體：**量測失敗時給出一個看起來正常的數字**。
> 這種失敗比報錯危險得多。凡是取數，都要先問「失敗的時候長什麼樣子」。

### 磁碟（與記憶體分開判，不得互相抵充）

**可清除快取與真實資料分開回報，快取不計入需求。**
〔事證：某機套件管理器快取 63 GB、容器磁碟映像 11 GB、本機模型權重 9.4 GB、程式碼索引 1.2 GB；
既有個案據此判定標準儲存配置已足，不加購〕

## 四層歸因

每一項佔用都必須落到一層。**未分類者一律視為 L1。**
非 agentic 負載（瀏覽器、桌面 app、編輯器）**一樣要分類，不得豁免為背景常數**
〔事證：裝置 A 的瀏覽器 57 個 process 佔 4,075 MB，單獨吃掉的量超過整輪開發工具優化省下的全部〕。

> ⚠️ **以下的事證是「某台機器的觀測」，不是通則。** 換一台機器，同一個位置可能空無一物。
> 兩台已知的落差：
>
> | 現象 | 裝置 A（重負載） | 裝置 B（閒置型） |
> |---|---|---|
> | 容器化 MCP server | 12 個並行 fork、926 MiB | **0 個（沒裝容器執行環境）** |
> | 瀏覽器 process | 57 個、4,075 MB | 11 個 |
> | 最大單一消耗者 | agentic 相關 | **非 agentic（資安代理），且是 CPU 不是記憶體** |
>
> ⛔ **不要照著事證去找對應的東西。** 先分層，落到哪層算哪層；
> 事證是用來說明判準怎麼套，不是用來當清單勾。

| 層 | 判準 | 處置 |
|---|---|---|
| **L1 純浪費** | 無對應的活著 client／同一能力被重複定義／設定缺陷造成的額外佔用／**未經演練的備援** | 清到零，**且必須修成因**，重開機後複測仍為零 |
| **L2 習慣驅動** | 隨「開了幾個 X」線性增加，且 ≥1 個長時間無活動 | **多半是第一層行為問題的投影，回 `behavior.md` 處理**〔事證：某機 12 個並行 session 各自 fork 一個容器化 MCP server，合計約 926 MiB。每個容器都有活著的 client、都不是浪費 —— 但總量由「同時開幾個 session」決定，所以解法在第一層不在第二層〕 |
| **L3 架構選擇** | 同能力有不需常駐的替代實作（遠端 API／http transport／原生執行／冷載入） | 先修正設定再做 A/B；未通過者不計入基線 |
| **L4 不可壓縮** | 關掉後成功率下降／帳單上升／離線不可用（**實測，非自陳**） | 唯一構成缺口的項目 |

```text
應然基線 = Σ(L4)
         = 現值 − Σ(L1) − Σ(L2 可削減) − Σ(L3 未過 A/B)
```

⛔ **不得以現值作為需求基準** —— 現值可能已經包含該被刪掉的浪費。
⛔ **不得跳層**：L4 的主張，只有在 L1–L3 全部處理完並複測之後才被受理。

### L1 的五條

- **必須修成因，不得以「已手動清除」結案**
  〔事證：某機的容器化 MCP server，其孤兒回收條件是「host 上完全沒有任何活著的 client」。
  這個條件在多 session 環境下幾乎不會成立，於是**已死 client 留下的孤兒也一併回收不掉**，
  要等所有 session 都關掉才有機會。手動清一次不會改變這個結構〕
- ⛔ **不得從「數量多」或「存活久」推論是孤兒，必須實際驗證對應的 client 還在不在**
  〔事證：同一台機器上，12 個容器（其中多個 uptime 超過 20 小時）一度被判定為孤兒，
  實測後發現有 **12 個活著的 client、1:1 對應、已退出殘留 0 個** —— 它們全部正在被使用。
  容器活很久只代表那個 session 開很久。**照那個誤判執行刪除，會直接弄壞 12 個進行中的 session**〕
- **必須驗證「宣稱做過的優化現在還在生效」，且須持久化在設定檔而非 shell session**
  〔事證：某份申請書列「本機模型服務改為閒置 60 秒即釋放」為已完成措施，
  但實測對應環境變數在 launchd 設定與所有 shell 設定檔中**都不存在**，仍走預設值〕
- **必須逐項清查同一能力的重複定義**
  〔事證：某機有兩個服務各被定義兩次（一次 stdio、一次 http），那是設定衝突而非兩套並用〕
- **必須把「錯誤設定造成的額外佔用」列為 L1，即使其宿主是 L3 或 L4**

### L3 的兩條

- **A/B 兩臂必須同時回報四項，缺一不受理**：任務成功率、端到端完成時間、端到端帳單、常駐 footprint。
  **單看第四項判定者，判定無效** —— 這是既有原則「壓縮率 ≠ 成本節省，
  以任務成功率＋端到端帳單為準」（見團隊既有規範）在記憶體軸的同構物
- ⛔ **不得以 transport 型態推論本機成本**
  〔事證：走 OAuth 的 remote MCP 仍靠本機 bridge process 轉接，實測有 2 個在跑 ——
  「改用 remote 就不佔記憶體」是錯的〕

## 症狀 → 歸因 → 動作

**必須先做瓶頸歸因，再談任何動作。**

| 症狀 | 歸因 | 指名動作 |
|---|---|---|
| `λ` 高、CPU 使用率低、`ρ` 或 `σ` 高 | I/O 等待來自分頁 → **記憶體瓶頸** | 走完整流程；**提高 CPU 規格無效** |
| `λ` 高、單一 process CPU 近 100%、`φ` 正常 | **運算瓶頸，非記憶體** | 先查該 process 是否應走 GPU／加速路徑〔事證：某機本機推論實測跑在 CPU 100% 而非 GPU〕；此時升記憶體不會修好它 |
| `φ` 低但 `ρ`、`σ` 都低 | 記憶體被佔滿但無壓力（多為快取） | 不需處理，不構成升規理由 |
| process 數 = session 數 × N，多數 session 長時間無活動 | L2，且是第一層的投影 | **回 `behavior.md`**；順帶檢查 stdio→http 是否可去除 per-session fork |
| 同一能力出現兩份定義 | L1 重複設定 | 設定去重 |
| 容器有殘留 | **先驗證再歸因**：逐一比對容器與其 client 是否還活著 | 確認是孤兒才修清理條件的判定邏輯（不是手動清）；⛔ 不可用「容器數多」或「活很久」推論 |
| 磁碟將滿 | 多為可清除快取 | 先清快取，不構成升規理由 |
| remote MCP 但本機仍有負載 | bridge process | 實測列舉，不得以 transport 型態推論 |

### 可照列的第一方設定手段

本機模型的存活時間與並行數上限、GPU 卸載設定、容器 VM 記憶體上限、
MCP 設定去重與 stdio→http 收斂、容器自動清理條件、
瀏覽器記憶體節省模式與預先載入、編輯器擴充套件依用途分流、並行 session 上限、定期重新開機。

⛔ **不列外部 OSS 候選工具名單。** 治理數字（維護狀態、貢獻集中度）會過時，
列出來等於發出「條件成熟可以試」的錯誤訊號。要引入新工具時**當場查證**，三條判準：

1. **星數不可信**，要看 watcher:star 比，而且比率自己算、跟同期同類工具比，不要套寫死的門檻
2. **工具自報的效能／節省數字不可信**，以任務成功率＋端到端帳單為準
3. **安裝前核對官方 org namespace 並 pin 版本**（假冒套件在此領域活躍）
