### 修訂 1｜G0 的 `inconclusive` 處置（2026-09-03）

| | |
|---|---|
| **原規則** | 四項判據在**每一個**取樣點都一致指向運算 → 不受理 |
| **新規則** | 沒有任何判據指向記憶體，**且**至少一個取樣點四項全指向運算 → 不受理 |
| **前一版 commit** | `786aab0`（2026-09-03T18:18:28+08:00） |
| **觸發** | 標準第一次真的被套用 |

**發現的過程**：某台機器取了三個時點、12 個判據讀數，其中 **11 個指向運算、0 個指向記憶體**。
但取樣 3 落在閒置時刻（突發的 CPU 消耗者剛結束，`single_cpu` 因此標成 `inconclusive`），
所以「每一個取樣點都四項全 compute」不成立，已登記的邏輯輸出「無法歸因」。

**為什麼原規則錯了**：G0 問的是「瓶頸是不是記憶體」。
**沒有任何一項指向記憶體時，這個問題已經有答案了。**
閒置時刻的 `inconclusive` 代表「那一刻沒有瓶頸」，它不是反面證據，
不該把一個明確非記憶體的案子救回「無法判定」。
而且一台完全沒有瓶頸的機器當然不需要升規 —— 判它不受理是對的。

**為什麼這不是為了讓那台機器過關而裁剪**（三項可查證）：

1. **方向相反。** 修訂讓標準**更容易判不受理**，不是更容易受理。
   為了想要的答案裁剪標準會往受理的方向偏，這一次往反方向。
2. **對有記憶體證據的機器不生效。** 那些案子走情況 3／4，結果與修訂前完全相同。
   ⛔ 修訂不得改變任何既有案子的結論 —— 這是修訂的驗收條件，有測試守著。
3. **窮盡且互斥。** 四種情況覆蓋所有輸入組合，沒有留下「看情況」的空間。
   原規則的問題正是它沒有規定 `inconclusive` 該怎麼算。

**留下的教訓**：⛔ **判準裡出現「一致」「全部」這種量詞時，要同時規定第三種值怎麼算。**
原規則只想過 `memory` 與 `compute`，沒想過 `inconclusive`，於是程式碼替它做了決定
（往嚴的方向），而那個決定沒有被任何人審過。

### 修訂 2｜G0 改為兩組正面證據；`observation` 允許當下使用證據（2026-09-03）

| | |
|---|---|
| **前一版 commit** | `f2e1c6e`（2026-09-03T18:32:48+08:00） |
| **觸發** | 標準第二次被套用（裝置 A） |

#### ⚠️ 先說方向：這次修訂有利於申請方

**修訂 1 的方向是讓標準更容易判不受理，我當時拿「方向相反」當它不是裁剪的證據之一。
這一次方向相反 —— 它把裝置 A 從「停住」變成「過」，而裝置 A 正是提出需求的那一台。**
所以這次不能拿方向當證據，只能靠論證本身站住。這段話必須出現在審查文件的最前面，
⛔ 不得只藏在這裡。

#### 改了什麼

**(a) G0 從「四項判據投票」改為「兩組正面證據」。**

原判據表的兩欄不對稱。以判據 3 為例：

| 機器狀態 | `ps` vs `pgrep` |
|---|---|
| 完全閒置、無瓶頸 | 一致 |
| CPU 打滿 | 一致 |
| 記憶體吃緊但未達截斷門檻 | 一致 |
| 記憶體壓力嚴重到截斷 `ps` | 差距大 |

**「一致」跟每一種狀態都相容，鑑別力是零。** 把它標成「指向運算」是**製造訊號** ——
與 A1–A4「量測失敗時給出一個看起來正常的數字」同型，這次是
「缺乏證據時給出一個看起來像證據的標籤」。判據 1（`Swapouts = 0`）與
判據 4（無高 CPU process）有同樣的不對稱。

後果是實測出來的：裝置 A 三項指向記憶體、判據 3 因為 `ps` 沒被截斷而標成「指向運算」，
於是被判「矛盾、無法歸因」。**任何記憶體壓力還沒嚴重到截斷 `ps` 的機器都會被這樣擋掉**，
而那是絕大多數的案子。

**(b) `observation` 允許當下使用證據。**
原本只收歷史痕跡（失敗紀錄、重跑次數），但那與 R2「當下現況優先、不改機器去累積資料」
直接矛盾 —— 要求提案者拿出歷史，等於要他先累積資料。
改為當下使用證據優先。⛔ 但**當下有在用 ≠ 不可壓縮**：使用證據只讓項目進入候選集，
L4 的認定仍由 G2 的降載實驗決定。這個護欄沒有放寬。

#### 為什麼這不是裁剪（可查證的部分）

1. **裝置 B 的結論不變。** 有測試守著
   （`test_device_b_verdict_is_preserved_by_the_revision`）：B 的形態是
   `C1` present、記憶體證據全 absent，其中一個取樣點連 `C1` 都 absent（突發結束）——
   仍判不受理。
2. **`absent` 與 `unknown` 都不得產生任一方的證據。** 兩條測試守著。
   新結構沒有把「沒有證據」變成「有利的證據」，它只是不再把它變成**不利的**證據。
3. **四種組合窮盡且互斥**，沒有留下「看情況」的空間。
4. **G2 的護欄沒動。** 降載實驗、≥10 個任務、無劣化就退回第一層，全部原樣。
   G0 只決定「這個案子屬不屬於記憶體軸」，不決定缺口成不成立。

#### 留下的教訓

⛔ **判準的每一欄都要問「這個值有鑑別力嗎」** ——
即「處在其他狀態時，這一欄會不會長得一樣」。答案是「會」的話，那一欄不是判據，
把它寫成判據會製造訊號。

⛔ **要求提案者拿出歷史證據，與「不改機器去累積資料」是同一件事的兩面。**
判準之間會互相矛盾，寫的時候要橫向對照。

### 修訂 3｜宣告工作集、宣告式規格階梯、以及壓艙物的方向限制（2026-09-03）

| | |
|---|---|
| **前一版 commit** | `ed07906`（2026-09-03T18:51:57+08:00） |
| **觸發** | 第一次要為一台真實機器產出機型建議 |

#### ⚠️ 方向：前兩項有利於申請方，第三項是限制

#### (a) 宣告工作集：四層模型逼每項只落一層，但有些項目本質是混的

瀏覽器是最清楚的例子：**工作真的需要的 N 個視窗（不可壓縮）＋累積下來的 M 個（習慣驅動）**。
整項塞 L2 低估基線，整項塞 L4 高估。標準其實已經有解這個形狀的機制 ——
`scales_with_concurrency`（宣告一個上限、計入上限內的量、超出的算 L2）——
把它推廣成「任何可宣告的工作單位」就解決了。

⛔ **這不是把 L2 洗成 L4。** 三層護欄都在：要有 `observation`（當下使用證據）、
只計宣告的那一段、而且**是不是真的不可壓縮仍由 G2 決定**。四條測試守著。

#### (b) 宣告式規格階梯

原本只有證否式。加入 `declared_headroom`：覆蓋應然基線的那一階，再加一階。
⚠️ 比證否式寬鬆。唯一的硬要求是**錨點必須是應然基線**，
有測試守著（`test_headroom_anchor_must_be_the_baseline_not_current_usage`）——
用現值當錨點會把已認定的浪費一起買進去。

#### (c) 🔴 壓艙物只能往下，不能往上 —— 這讓證否式在升級情境下常常不可用

寫壓艙物腳本時撞到的：`--ceiling 24` 在一台 16 GB 的機器上直接被拒絕，
因為**壓艙物只能讓機器變小**。於是：

| 你想證明 | 測得到嗎 |
|---|---|
| 現有的 16 GB 不足 | ✅ 現況就在發生（換出速率、`Swapins`、失敗紀錄），甚至不需要壓艙物 |
| 某個宣告的 L4 項目其實可壓縮 | ✅ 把它關掉跑任務集 —— 這才是降載實驗的本行 |
| **下一階的 24 GB 不足** | ❌ **測不到。** 要在 24 GB 的機器上跑，而你手上沒有 |

**推論一**：`disproof` 政策在**升級**情境下結構上常常做不到 ——
除非借得到候選規格的機器。這不是偷懶，是量測方向的限制。
`declared_headroom` 因此不只是「比較寬鬆的選項」，而是**升級情境下唯一做得到的那個**。
⚠️ 但寬鬆是真的，審查文件要寫明。

**推論二**：G2 的降載實驗**換一個問題問**。它問的不該是「多大的機器才夠」
（測不到），而是「**這些宣告為不可壓縮的東西，真的不可壓縮嗎**」——
逐項關掉、跑任務集、看成功率。這個問題壓艙物答得了，而且答案會直接改寫應然基線。

**留下的教訓**：⛔ **寫下一個實驗協議之前，先問「這個實驗在物理上做得到嗎」。**
「降載實驗證明下一階不足」在紙上讀起來很嚴謹，寫成腳本才發現方向是反的。
條文的嚴謹度不等於可執行性。

### 修訂 4｜G1 的候選集完整性（2026-09-03）

| | |
|---|---|
| **前一版 commit** | `a9ffa8a`（2026-09-03T19:09:37+08:00） |
| **觸發** | 第一次真的跑完一個 L3 候選的 A/B（`ollama` 冷載入） |

#### ✅ 方向：這次修訂**不利於申請方**（讓 G1 更難過）

前兩次修訂的方向有利於申請方，這一次相反。

#### 發現的過程

`ollama` 的 A/B 跑完之後 G1 就過了 —— 但當時的案子裡**只有 `ollama` 一個 L3 候選**，
因為分析者（我）把 `cortex` 與 `mem0` 歸在「容器/VM」並標成 **L4**，
於是它們從來沒面對 A/B。

而 `environment.md` 對 L3 的定義是「同能力有**不需常駐的替代實作**
（遠端 API／**http transport**／原生執行／冷載入）」——
`cortex` 目前是 stdio 每 session fork 一個容器，**stdio→http 正是那樣的替代**。
所以它本來就該是 L3 候選。

**原 G1 的漏洞**：它檢查「列出來的每一列四欄齊不齊」，
不檢查「該列的候選有沒有全部列出來」。兩個後果：

1. 只測最好測的那一個候選就能過關
2. **把項目歸成 L4 就能讓它完全退出候選集** —— 這個更嚴重，
   因為它讓整道 A/B 變成可選的

#### 改了什麼

- 候選集改為**宣告與實測的聯集**，且宣告項必須正面回答
  `non_resident_alternative`（省略即不過）
- 候選集沒跑完 → G1 不過，並指名漏了誰
- A/B 必須給 `alternative_disproved`
- **基線同步加牙齒**：替代未被否證的項目不得計入應然基線。
  只讓 G1 不過是不夠的 —— `R` 會繼續虛報，而 `R` 是提報給審查者看的數字

#### 對本案的影響

`cortex` 與 `mem0`（合計 2,560 MB）退出基線，改記 L3 待驗，G1 由過變成不過。
⚠️ 但**建議機型不變**：基線 19.8 → 17.3 GB，覆蓋階仍是 24，加一階仍是 36 GB。

#### 留下的教訓

⛔ **一道閘門要求「每一項都要有 X」時，同時要規定「哪些項算在內」。**
前者是列的完整性，後者是集合的完整性 —— 只寫前者，分析者可以靠縮小集合過關。
這與修訂 1 的教訓同型（量詞沒規定第三種值），都是**條文沒把邊界寫完**。

⛔ **閘門不過的同時，數字也要跟著修正。** 只擋住結論、不修正 `R`，
審查者看到的仍是虛報的缺口。判準與提報量要一起改。

### 修訂 5｜劣化定義量不到的項目要指名，不得默默算成已驗證（2026-09-04）

| | |
|---|---|
| **前一版 commit** | `cbebad1`（2026-09-03T20:5x） |
| **觸發** | 第一次真的為一個宣告項設計 G2 的實驗 |

#### ✅ 方向：不利於申請方（讓 G2 更難過）

#### 發現的過程

修訂 4 剛補上「工作集縮減」形態來處理「整項關不掉」的項目。
接著使用者宣告：**瀏覽器分頁就是待辦佇列，逐頁解決中，不可再減少。**

於是兩種形態都用不上：整項移除不可能（前提），工作集縮減也不可能（工作集＝當下現況）。
更關鍵的是**第三件事**：就算硬把分頁關掉去跑任務集，
**任何任務都不會失敗** —— 代價是工作佇列遺失，而已登記的劣化定義 A
（任務成功率：OOM／process 被殺／工具呼叫失敗／需要重跑）**量不到那種代價**。

**這不是實驗形態的問題，是劣化定義與被測項目不匹配。**

#### 改了什麼

- 宣告項可帶 `g2_unvalidatable: {"reason": "..."}`
- `unvalidatable_items()` 算出每個不可驗項目**佔應然基線的百分比**
- G2 **停住並指名它們**，即使降載實驗跑完且有劣化也一樣
- 降載還沒跑時就先講「跑完那幾項仍不會被驗證」，⛔ 不讓人以為跑完就解決了

#### 為什麼不是讓它默默通過

那 10,744 MB 佔基線 **50.9%**。若讓它默默算成已驗證，審查者看到的是
「缺口 20.6 GB 已驗證」，實際上**超過一半是未驗證的宣告**。
指名它、算出佔比，審查者才有得判斷。這正是 G2 存在的理由。

#### 留下的教訓

⛔ **挑劣化定義時就要問「這個定義量得到每一個宣告項的代價嗎」。**
規則本身已收進第五節（含定義 A 看不見的那兩類），此處不重述。

⛔ **一個項目不可驗時，正確處置是指名它並停住，不是繞過它。**
繞過會讓「已驗證」與「沒驗過」在報告上長得一樣 —— 那是 A1–A4 的家族換了一層。

### 修訂 6｜建議的形狀：保留工作習慣、查證現成方案、迴圈到資訊齊全（2026-09-04）

| | |
|---|---|
| **前一版 commit** | `fef8c16` |
| **觸發** | 使用者對判準方向的糾正 |

#### 發現的過程

修訂 5 剛把「分頁即待辦佇列」標成 G2 不可驗，並在回報裡附了一個
「這是 L3 形狀的問題」的觀察 —— 暗示待辦佇列可以不放在瀏覽器裡。
使用者糾正：**判準不應該透過要求改變工作習慣來給建議。**
不同人、不同環境、不同工作情況，skill 的目的
是透過核心本質給優化建議，真的無法才進到換機。

而實際查證立刻證明他是對的：**保留習慣、降低成本的方案是現成的**
（Chrome Memory Saver —— 分頁全留、只卸載閒置 renderer），
甚至**已經在那台機器上開著**。判準一直在問「這一項能不能拿掉」，
正確的問題是「**有沒有辦法保留這個工作習慣、同時降低它的實作成本**」。

#### 改了什麼

`SKILL.md` Step 3 新增「建議的形狀」三條硬規則（見該節）：
不改習慣、給可執行步驟＋允許網路查證（先查現況再建議）、迴圈到資訊齊全才下結論。

#### 留下的教訓

⛔ **habit 與 cost 是兩層，不可混判。** 「這個工作方式佔 10 GB」不表示
要改工作方式 —— 先找「同樣的工作方式、更低的成本」的實作。
兩層都窮盡了，才輪到換機。

⛔ **提出任何方案之前，先查它在這台的現況。**
已啟用的方案被當成新建議提出，會讓整份報告的可信度歸零 ——
讀的人會問「你到底有沒有看過我的機器」。

⛔ **「renderer 數＝分頁數」是錯的等式。** Memory Saver 丟棄的分頁不佔 renderer，
所以 renderer 是「已載入的子集」，分頁列（使用者的佇列）可能大得多。
量測層的名詞要對應到使用者語言的名詞時，先驗證對應關係。

修訂 6 的迴圈跑到底之後，瀏覽器項目拿到了**機制級證據**：
Chrome 自己拒絕回收那些分頁（`chrome://discards` 大部分列 Is Discardable ✗，
View Reason = form data）—— 平台以保護未儲存狀態為由拒絕回收，
這比任何 10 個任務的行為實驗都更直接地回答了「拿掉它會怎樣」：會遺失工作狀態。

同時 Apple 系統／強制合規的資安代理／宣告的工作負載本身，
從來就不可能有意義地「關掉跑任務集」—— 原設計把它們硬塞進單一實驗形態，
是修訂 3(c)（實驗要在物理上做得到）與修訂 5（劣化定義要量得到代價）的同型問題。

#### 改了什麼

每個**計入基線**的項目都要有一列驗證，型別三選一：
`downclock`（預設，沒填的都落在這裡）／`mechanism`（要指名平台機制＋列出試過的桿子）／
`structural`（basis 限定：作業系統／強制合規／宣告的工作負載本身）。
⛔ 「我宣告它重要」仍然不是任何一種型別。
⛔ 驗證由 **counted 驅動**不由宣告驅動 —— 第一版由宣告驅動時，
呼叫端漏傳宣告會讓 pending 為空、G2 反而直接過（空宣告讓閘門變鬆），
這個語意漏洞有回歸測試守著。

#### 不變性作為合法收斂

G2 仍可停在「部分項目待降載」。此時**若機型建議對所有未決分支不變**
（逐分支算給審查者看），迴圈即可收斂 —— 繼續實驗只是花成本買一個不會改變的答案。
〔事證：某案 mem0＋Docker VM 待驗，但全部計入 20.6 GB 與最保守分支 16.7 GB
落在同一覆蓋階（24）→ 建議同為 36 GB〕
⛔ 不變性要**逐分支列出**，不得只寫「反正都一樣」。

#### 留下的教訓

⛔ **單一實驗形態塞不下所有驗證需求。** 三次撞牆（測不到更大的機器、
劣化定義量不到狀態遺失、OS 不可能關掉跑任務）都是同一個病：
把「驗證」與「某一種實驗」劃了等號。驗證的本質是「拿掉它的代價有指名的證據」，
實驗只是取得證據的方法之一。
