# 可攜性：換一台機器之前先讀這個

**判斷依據**：每一次把本 skill 套到新的人或新的機器，先跑完本檔的前置檢查。
**套用方式**：本檔 + `scripts/scan_sessions.py --preflight` + `scripts/probe_host.sh`。

> v0.1 只被**一台重負載機器**（裝置 A）校準過。第二台是**閒置型**機器（7 個 session、
> swap 未配置、瓶頸在 CPU 不在記憶體），v0.1 在那台上失效或誤判了 **14 次**。
> 本檔起初就是那 14 次的清單，以及不再犯的兩條規則。
>
> **這份清單是活的，目前 16 類。** 第 15 類（A4）不是換機器踩到的，
> 是**回到裝置 A 複量時**才踩到的；第 16 類（F1）是**新增工具時**踩到的 ——
> 換版本、換 session 型態、換工具，一樣會冒出新的失效。
> ⛔ 所以「這台跑過了」不等於「這台以後都沒問題」。

---

## 怎麼讀這份清單

**三個欄位的性質不同，混讀會誤用**：

| 欄位 | 性質 | 怎麼用 |
|---|---|---|
| **失效** | **通則** —— 這一類的形狀，跨機器成立 | 拿它去對你的工具與環境 |
| **事證** | **某台機器的觀測** —— 只是「這個形狀長什麼樣」的一個實例 | 用來理解形狀，⛔ **不是前提條件也不是檢查項** |
| **修法** | 已實作在本 repo 的做法 | 可照抄，但要確認它在你的環境成立 |

⛔ **不要照著事證去找對應的東西。** 事證寫「某機用 `codebase-memory`」「7 個 session」
「12 個容器」，換一台機器那些具體物可能全都不存在 —— **失效類型仍然成立**。
先看形狀，再問「我這裡的對應物是什麼」。
（這是 `environment.md` 四層歸因那段的同一條規則，套用在本檔自己身上。）

⛔ **這 16 類不是窮盡的，對完不等於安全。** 它是**已經踩過**的清單，不是所有可能失效的
分類法。對完 16 類只保證「不再犯已知的錯」；沒踩過的失效**只有量測與交叉驗證抓得到**。
⚠️ 把它當完備檢查表用，就是 F1 的變體 —— 用一份文件替代思考。

## 兩條規則

### R1｜UNKNOWN ≠ 0

**量不到的東西一律回 `UNKNOWN` + 原因，不得回 0。**

這條看起來像潔癖，實際上是本 skill 最貴的一課。`0` 在本 skill 裡是有意義的訊號
（「有索引卻不用」是行為問題），所以把「量不到」也寫成 `0`，等於**偽造一個行為旗標**。

索引使用是最清楚的例子。三種狀態在 v0.1 全部長成 `index_use: 0`：

| 主機狀態 | 正確輸出 | 該怎麼處置 |
|---|---|---|
| 沒有任何索引型 MCP | `UNKNOWN（未設定）` | **不是行為問題。不得命中硬旗標** |
| 有設定、process 活著、0 次呼叫 | `0` + 🔴 旗標 | **是行為問題。指名並給建議** |
| 有呼叫 | 次數 | 正常 |

注意第一列與第二列**光看歷史語料分不出來** —— 必須知道主機當下裝了什麼。
這就是 R1 為什麼需要 R2。

### R2｜當下現況優先，不改機器

**本 skill 不得要求修改任何主機設定來累積資料。**

語料是什麼就是什麼。不足、被保留期截斷、涵蓋期太短 —— **聲明限制、限縮結論範圍**，
然後把判斷重心移到當下現況的 live probe。要機器改設定來配合工具，方向是反的。

推論：

- ⛔ 不得輸出「建議延長 session 保留期」這類建議
- ⛔ 不得把「兩週後再跑一次比較」當成必要步驟
- ✅ 複測 = **當場重量**（分鐘級），見 `SKILL.md` 的三層閘門

這條也有實測背書。同一次診斷裡：

| 來源 | 產出 |
|---|---|
| 歷史語料（7 session／2,384 行） | 五個指標，全部只能標「暫定」 |
| **當下現況 probe** | 瓶頸歸因（防毒常駐吃掉 2.5／8 核）、3 處設定重複、系統擴充孤兒、`Swapouts` = 0、0 容器 |

**結論全部由 probe 決定，語料只提供背景。**

## 前置檢查

```bash
python3 scripts/scan_sessions.py --preflight   # 語料側：量得到什麼
./scripts/probe_host.sh                        # 主機側：當下現況（macOS）
```

`--preflight` 會回答四個問題，四個都要看過才可以相信後面的數字：

| 問題 | 答案是這個就要小心 |
|---|---|
| 這台有沒有索引型 MCP？ | `UNKNOWN` → 指標 1 的硬旗標不成立，不得據此判行為問題 |
| 當前 session id 解得出來嗎？ | `UNRESOLVED` → `--exclude-current` 不能用，改用 `--session-id` |
| repo roots 掃到哪些？ | 少了你知道存在的 repo → 用 `--repo-root` 補 |
| 語料被保留期截斷了嗎？ | `corpus_truncated: true` → 結論只是這個視窗內的下界 |

## 16 類跨裝置失效

### 五個家族（母原理 —— 新失效先從這裡找位置）

16 類是按**發現批次**堆起來的，但它們收斂成五個家族。
遇到不在清單裡的失效時，⛔ **先問它屬於哪個家族，再決定加在哪**：

| 家族 | 母原理 | 涵蓋 |
|---|---|---|
| **Ⅰ 量測失敗時給出看起來正常的數字** | 失敗要長得像失敗。取數前先問「失敗的時候長什麼樣子」 | A1–A4、`environment.md` 陷阱四／五／六 |
| **Ⅱ 寫死的主機假設靜默失效** | 任何「這台一定有 X」的假設，換機器就是靜默的空集合 | B1–B3 |
| **Ⅲ 小樣本上的統計不成立** | 樣本不足時不輸出門檻，比輸出一個算不出來的門檻好 | C1–C3 |
| **Ⅳ 觀測者效應** | 工具會改變它要量的對象，先量自己 | D1–D2 |
| **Ⅴ 修法不會自動傳播** | 清單是文件不是檢查，它攔不住新程式碼 | E1–E3、F1 |

**新失效的歸類路徑**：

1. 它是「量到了但值是錯的」→ 家族Ⅰ。⛔ 這一族最優先，因為它會偽裝成正常訊號
2. 它是「換個環境就消失／永不觸發」→ 家族Ⅱ
3. 它是「樣本不夠卻算了」→ 家族Ⅲ
4. 它是「因為我去量所以變了」→ 家族Ⅳ
5. 它是「這個錯以前修過，換個地方又出現」→ 家族Ⅴ
6. **五個都不像 → 那可能是第六個家族**，把母原理寫出來再加類型。
   ⚠️ 硬塞進既有家族會讓母原理失焦，比多開一個家族糟

📌 家族比類型更耐久。**類型會隨工具增加，母原理不會** ——
所以套用到全新的環境（別的 harness、別的 OS、別的工具鏈）時，
帶得走的是這五條，不是那 16 行。

### A. 靜默回 0 的假陰性（最危險 —— 會偽裝成行為旗標）

| # | 失效 | 事證 | 修法（A1–A3 為 v0.2，**A4 為 v0.2.1**） |
|---|---|---|---|
| **A1** | 索引 MCP 白名單寫死 server 名稱。換一台機器換一套索引工具就靜默失效 | 某機用 `codebase-memory`，白名單三個名稱一個都沒出現；564 次工具呼叫命中 0 → 得到一個假的 🔴 硬旗標 | 樣式清單可外掛（`scripts/index-mcp-patterns.json`）+ 從主機 MCP 設定實際發現 + 三態輸出 |
| **A2** | `--exclude-current` 只讀一個環境變數名。該變數不存在時**靜默無作用** | 某機的變數名是 `CLAUDE_CODE_HOST_SESSION_ID`，`CLAUDE_SESSION_ID` 不存在 → 診斷用的 session 汙染了自己的統計，且無任何提示 | 三段解析 + 解不出來時**非 0 退出**（大聲失敗） |
| **A3** | `vmmap` 對受保護 process 回空字串，而規範要求「一律取 `phys_footprint`」，沒有 fallback | 防毒的主 process `vmmap` 回空，只能用 RSS 當下界 —— 那是全機最大的消耗者 | 見 `environment.md` 陷阱六：footprint 標 UNKNOWN，退回 RSS 並**明確標為下界** |
| **A4** | **解得出來但解錯**：`resolve_session_id` 的清單缺 `CLAUDE_CODE_SESSION_ID`，而那才是命名 jsonl、也出現在每筆記錄 `sessionId` 欄的那一個。A2 加的 loud-fail **不觸發**，因為的確解出了一個 id | 裝置 A 的 v0.2.1 複量：`CLAUDE_SESSION_ID` 未設定、`CLAUDE_CODE_HOST_SESSION_ID` = `local_<uuid>`（帶前綴，對不上任何 jsonl）。`session_id_resolved: true`、`excluded_src` 有值，排除卻是 no-op。背靠背四種呼叫證實：`--exclude-current` 得 252 個 main session，帶正確 `--session-id` 才得 251 | ① 清單補進 `CLAUDE_CODE_SESSION_ID` 並置於最前（止血）；② **`session_id_in_corpus()`：解出的 id 要對著語料驗證**，對不上就比照「解不出來」大聲失敗（通用修法）；③ `--preflight` 新增 `session_id_matches_corpus`；④ `--session-id` 單獨給定即生效 |

> A1–A4 全是 `environment.md` 自己「陷阱四：失敗時可能靜默回 0」的同型錯誤，
> **發生在 skill 自己的工具裡**。寫得出那條陷阱不代表自己不會犯。
>
> A4 另外示範了一件事：**A2 的修法本身也會被繞過**。A2 加的是「解不出來就大聲失敗」，
> 但它預設「解出來 = 解對了」。⛔ 所以修法不可以只加一個變數名 ——
> 那與 A1（白名單寫死 server 名稱）是同一種病，下一台機器換個名字就再犯。
> 真正可攜的判準是**問語料**，不是問環境變數：`session_id_in_corpus()` 不需要知道
> 任何變數名，換機器、換 id 命名規則都仍然成立。

### B. 寫死主機假設

| # | 失效 | 事證 | v0.2 的修法 |
|---|---|---|---|
| **B1** | repo 根目錄寫死 `~/Work/Code` 等路徑，且只掃 depth 1 | 某機的專案在 `~/Work/<x>/codebase/<y>`（depth 3），掃不到 → 那些 repo 底下的探勘全部沒被算成程式碼探勘 | 四來源**聯集**：家目錄限深掃描（含剪枝）＋ projects 目錄名反解 cwd ＋ 當前 git repo ＋ `--repo-root` |
| **B2** | `environment.md` 全是 macOS 指令，但沒宣告平台範圍 | CI 跑在 Linux，環境層完全無法自動驗證 | `environment.md` 開頭明文宣告平台；其他平台走本檔的自陳版 |
| **B3** | `σ` = swap 已用／上限，在 swap 未配置的機器上是 `0/0` | 某機 `vm.swapusage` 的 total 是 0.00M → `σ` 是 **UNDEFINED 不是 0** | `σ` 標 UNDEFINED；改以 `Swapouts`（自開機單調遞增）為主判據 |

### F. 修法未傳播（🔴 最容易再犯的一類）

| # | 失效 | 事證 | 修法 |
|---|---|---|---|
| **F1** | **一個類型的修法只套在當時那支工具上，之後新增的工具重犯同一類型。** 失效清單本身不會攔住新程式碼 —— 它是文件，不是檢查 | v0.3 新增 `select_task_set.py` 時**同時重犯 A1 與 D2**：<br>• **A1**：`WORK_TYPES` 寫死 `mcp__gitlab__…`、`mcp__youtrack__…`，甚至一個本機專屬的 connector UUID `mcp__606dcce5-…__content_read` → 換機器那些名字全不同，對應型態**靜默永不命中**，分類默默退化成「未分類」而不報錯<br>• **D2**：完全沒有排除當前 session 的機制（關鍵字命中 0），診斷自己就在母體裡、可能被選為實驗任務。當次剛好沒中 —— **沒中不代表機制存在** | ① `WORK_TYPES` 改為比對**協議層能力字串**（`merge_request`／`issue`／`document`…）＋外掛檔 `work-type-patterns.json`，與 A1 同一修法<br>② 排除機制**沿用** `scan_sessions.py` 已修好的 `resolve_session_id()` 與 `session_id_in_corpus()`，⛔ 不重寫 —— 重寫等於再犯第 15 類<br>③ **新增工具的驗收條件：拿本檔逐類對它自己一次**，這一條寫進下方注意事項 |

> **F1 是本清單唯一關於清單自己的一類。** 前 15 類都在講「換機器會壞掉」，
> F1 在講「換工具會壞掉」——**而換工具比換機器頻繁得多**。
>
> ⛔ 所以新增任何取數腳本時，驗收條件不是「它能跑」，
> 而是「**拿這 16 類逐項對它自己過一遍**」。這次是事後才對的，
> 於是兩類重犯都已經進了 commit 才被抓到。

| # | 失效 | 事證 | v0.2 的修法 |
|---|---|---|---|

## 觀測者效應規則

診斷工具本身會改變被診斷的對象。三條：

1. **先跑 `--preflight`，再 clone 任何東西到家目錄底下。**
   clone 進去就多一個 repo root，之後「什麼算程式碼探勘」的判定基準就變了。
2. **`--exclude-current` 一定要確認生效**，別假設它有效。
   `--preflight` 的「當前 session id」欄位要**兩件事都看**：
   顯示 `UNRESOLVED` 是沒解出來；顯示解出來了但
   `session_id_matches_corpus: false` 是**解錯了**，同樣沒生效（A4）。
   ⛔ 只看 `resolved` 會漏掉第二種 —— 那正是第 15 類失效的形態。
3. **診斷本身會膨脹語料。** 一次診斷可能貢獻上千行 session 紀錄，
   在只有幾千行的閒置機器上，那是可觀的比例。報告要寫明數字含不含本次診斷。

## 其他 harness：自陳版

**指標的概念可攜，自動量測不可攜。** `scan_sessions.py` 只讀 Claude Code 的 session 格式；
Cursor／Windsurf／OpenCode／Cline 等沒有同構的紀錄，在那裡跑不出任何數字。

⛔ **不要讓人以為跑得出來。** 掃到主機上有這些 harness 的設定目錄
（`.cursor/`、`.windsurf/`、`.opencode/`、`.clinerules/`、`.agents/` 等）時，
報告要明講「這部分是盲區」，並用下列問卷取得自陳。

自陳答案**標為自陳**，不得與掃描數字混在同一張表裡比較。

| 對應指標 | 問題 |
|---|---|
| 1 探勘繞道率 | 在那個工具裡找程式碼時，你是查索引／語意搜尋，還是讓它把檔案整個讀進來？ |
| 1 探勘繞道率 | 那個工具有沒有可用的程式碼索引？你開了嗎？ |
| 2 主 context 負載 | 探勘工作有沒有交給 subagent／子任務，還是都在主對話裡做？ |
| 3 context 膨脹 | 一個對話通常開多久才清？有沒有清過？ |
| 4 使用型態 | 一天大概開幾個對話？同時開著幾個？ |
| 5 重複操作 | 有沒有同一個檔案在一個對話裡被反覆讀進來的印象？ |
| 強度 | 一週大概用那個工具幾小時？ |

> 上游備註：`sync-targets.json` 已經預留了 `roo-code: .roo/rules`、`antigravity: .antigravity/rules`
> 這類多 harness 分發路徑，也就是這個 repo 早就預期 skill 會跑在不只一種 harness 上，
> 只是同步機制尚未實作。這份問卷是同步到位之前的權宜解。

## 裝置 profile

**門檻的樣本數就是這張表的欄數，不是量測次數。** 目前 **n = 2** —— 兩台**不構成分布**。
裝置 A 被量過兩次（v0.1 與 v0.2.1），那是**同一台的兩個時點，不是兩個樣本**。
這就是 v0.2 停止輸出跨裝置門檻的原因，不是保守，是算不出來。

### ⚠️ 同一台的兩次量測不可直接相比

繞道率 96 : 1 → 128.4 : 1 **不能讀成「行為變差了」**。
v0.2 把 repo root 從寫死路徑＋depth 1 改成四來源聯集（B1 的修法），
**分子的定義變了** —— 更多路徑被算成程式碼探勘。
方法變更與行為變化混在同一個數字裡，切不開。

⛔ **跨版本的同一指標，除非計算式沒動，都不得直接相比。**
要比行為就要用同一版腳本對兩個時點的語料各跑一次；本次沒有這樣做，所以只記錄不下結論。

〔這條的直接教訓：`SKILL.md` 的版本紀錄要寫清楚**哪些指標的計算式變了** ——
只寫「新增／改善」的話，下一個人就會把方法變更當成趨勢。〕

### profile 表原本缺機器識別

v0.2 的這張表沒有機器識別列，於是第三次套用時**無法回答「這是新機器還是同一台」**。
當時只能靠指標同型與單調變大來猜，而那是**從相鄰性推歸屬** —— 不成立。
最後是由人確認的。

已補上「機器識別」列。裝置 B 回填不了（當時沒記），**新的每一欄都必須填**。

每套用到**新的機器**，回來加一欄；同一台的複量寫進原欄位並標時點。
**加到 n ≥ 20 之前，不要恢復輸出跨裝置門檻。**

## 注意事項

- **隱私是硬要求**：`scan_sessions.py` 與 `probe_host.sh` 只輸出統計量與設定結構。
  跑在別人機器上時，**不得輸出任何對話內容、程式碼或業務資訊**。
- **兩支腳本都是唯讀**。看到可疑的東西一律回報，由人決定 ——
  第二層的動作多半不可逆，`environment.md` 明訂「做刪除動作之前，先用第二種方法確認要刪的東西真的是可刪的」。
- **失效類型是活的清單**。踩到新的一類，回來加一行，並在 `tests/` 加一個對應的 case ——
  沒有測試的條文，下一台機器會再踩一次。
- 🔴 **新增任何取數腳本的驗收條件：拿本檔的 16 類逐項對它自己過一遍。**
  這不是建議，是 F1 的直接後果 —— 清單是文件不是檢查，它不會自動攔住新程式碼。
  最少要問這四個：
  1. **A1**：有沒有寫死 server 名稱、connector UUID、或任何換機器就變的識別字？
  2. **B1／B2**：有沒有寫死路徑？平台假設有沒有明文宣告？
  3. **D2**：這支工具跑起來會不會改變它自己要量的東西？有沒有排除機制、而且驗證過生效？
  4. **A4**：需要 session id 的話，有沒有沿用既有的解析＋語料驗證，而不是重寫一份？
