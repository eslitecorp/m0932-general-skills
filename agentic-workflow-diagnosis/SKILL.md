# agentic-workflow-diagnosis — agentic 工作環境盡職調查

## 核心理念

**這是盡職調查，不是採購把關。產出是給提案者的建議報告，不是准駁結論。**

「在資源有限的機器上擴大 agent 使用」的答案主要不在硬體，在**使用方法**。
所以本 skill 的主體是**從實際使用紀錄找出工作流程的行為不當，並給出可執行的調整方法**。
只有在行為與環境調整都已窮盡、提案者仍明確反映必要，才走到第三層 ——
而第三層產出的是**遷就一個本不該存在的現況的權宜推薦**，不是本 skill 的成就。

| 是 | 不是 |
|---|---|
| 診斷使用方法，給具體調整建議 | 訂一套更難通過的採購門檻 |
| 讀者是**提案者本人** | 讀者是簽核者 |
| 「你的探勘方式讓 context 膨脹了，改成這樣」 | 「你不符合升規資格」 |
| 非不得已不花錢了事 | 用預算解決行為問題 |

## 三層診斷（順序不可跳）

```text
第零層  可攜性前置 —— 這台量得到什麼         → portability.md   ← 每次都做
   ↓
第一層  行為診斷 —— 使用方法對不對          → behavior.md      ← 主體
   ↓    改完 → 當場重量 → 仍不足才進下一層
第二層  環境診斷 —— 有沒有純浪費與錯誤設定    → environment.md
   ↓    改完 → 當場重量 → 仍不足才進下一層
第三層  缺口判定 —— 不得已的權宜推薦          → 見下方
```

**每一層都要求「改完 → 複測 → 仍不足」才可進入下一層。**
這就是「非不得已不花錢了事」的機制實現，不必靠形容詞勸人。

### 複測 = 當場重量

**複測是分鐘級的，不是跨週累積。** 每一條建議都必須附「當場可驗的動作 + 立即重量指令」：

| 動作 | 當場重量 | 期望 |
|---|---|---|
| MCP 設定去重 → 重啟 | `pgrep -f <server> \| wc -l` | N → 1 |
| hook 去重 | 重開一個 session 看注入次數 | N → 1 |
| 探勘改走索引 | 重跑 `scan_sessions.py` 看 `index_use` | 0 → >0 |

⛔ **不得把「兩週後再跑一次比較」當成必要步驟**，也**不得要求修改主機設定來累積資料**
（`portability.md` 的 R2）。這樣申請模式可以在一次會談內走完。

⛔ **不要跳過第一層。** 第二層清的是垃圾與錯誤設定，清完機器會好一點，
但不會改變使用方法 —— 跳過第一層等於用打掃代替檢討。

## 工作流程

### Step 1｜判斷模式

| 使用者說的 | 模式 | 做到哪裡 |
|---|---|---|
| 「agent 跑起來很卡」「我的工作流程哪裡有問題」 | **診斷模式** | 第一層 + 第二層的症狀對照表，30 分鐘內給建議。**不進申請流程** |
| 「要不要升規」「幫我評估硬體需求」 | **申請模式** | 三層走完，每層都要複測 |

### Step 1.5｜第零層：可攜性前置（每次都做，不可跳）

**必讀 `portability.md`**，然後：

```bash
python3 scripts/scan_sessions.py --preflight   # 語料側：量得到什麼
./scripts/probe_host.sh                        # 主機側：當下現況（macOS）
```

⛔ **不看 preflight 就直接讀指標，會把「量不到」讀成「量到 0」** ——
這兩件事在本 skill 裡的處置完全相反（`0` 是行為問題，`UNKNOWN` 不是）。

四個必看欄位：索引型 MCP 狀態、當前 session id 解不解得出、repo roots、語料有沒有被截斷。

### Step 2｜第一層：行為診斷（必做）

**必讀 `behavior.md`**，然後：

```bash
python3 scripts/scan_sessions.py
```

再補一次即時狀態（腳本不推算「還開著／未封存」）：用 `list_sessions` 取
`isRunning` / `isArchived` / `lastActivityAt`。

產出五個指標的實測值、命中的旗標、以及強度正規化後的值。
**樣本 `n < 20` 時不使用 p75／p90**，只用硬旗標與絕對值，並在報告寫明樣本量。

### Step 3｜給建議並要求當場重量

依槓桿大小排序，每條建議都要**可執行**且**附當場可跑的重量指令**。
**這一步不要一次給十條** —— 給最有槓桿的兩三條，重量後再談下一輪。

### Step 4｜第二層：環境診斷（第一層重量後仍不足才做）

**必讀 `environment.md`**。四層歸因、六個取數陷阱、症狀對照表都在那裡。

⛔ **進本層之前先過瓶頸歸因關卡**（見下方「不受理的判定」）。
歸因不指向記憶體的話，第二層的記憶體清查是白做的。

### Step 4.5｜不受理的判定（進第三層之前的關卡）

本 skill 只處理記憶體軸。**瓶頸不指向記憶體者不受理第三層** —— 這是邊界，不是推託。
判定用下面四項，**在不同負載時點各取一次，不得用單一快照**：

| # | 判據 | 指向記憶體 | 指向運算 |
|---|---|---|---|
| 1 | `Swapouts`（自開機累計） | > 0 且持續增加 | **= 0** → 洩壓閥從未開過 |
| 2 | `memory_pressure` 自報可用率 | 低 | **高** |
| 3 | `ps -ax` vs `pgrep -f .` 計數 | 差距大（`ps` 被截斷） | **一致** |
| 4 | 單一 process 瞬時 CPU（`top -l 2`） | 無特別高者 | **遠超 100%** |

四項一致指向運算 → **不受理，報告寫明並收在第二層**。
⛔ 此時升記憶體不會修好它；把降載實驗、共享替代、規格階梯套上去，是把證據放到錯的軸上。

四項互相矛盾 → 不要硬判，把四個值都列出來，說明無法歸因，並停在這裡。

〔事證：裝置 B 四項全部指向運算（`Swapouts` = 0 於 21 天 uptime、`memory_pressure` 77%、
772 vs 758 一致、單一非 agentic process 瞬時 246–326%），是本 skill 第一個不受理實例〕

### Step 5｜第三層：缺口判定（前兩層都窮盡，且提案者明確反映仍有必要）

- 缺口以**無因次比值**提報（`R` = 應然基線／實體容量、`ρ`、`σ`、`φ`），不寫死 GB
- **降載實驗（必做）**：刻意把佔用壓到容量以下，用 ≥10 個近期真實任務重跑。
  - 劣化 → 這就是「不升規會怎樣」的實測答案
  - 無劣化 → L4 分類錯誤，**退回第一層**
  - ⛔ 不得以「我覺得會很慢」代替
- **共享替代必答題**：能否由共用推論機／集中式服務滿足？
  理由須落在「資料落地限制／延遲不可容忍／離線可用性／供應商中斷降級」四者之一
- **規格階梯證否**：須證明「下一階較便宜的規格不足」，而非只證明本案規格夠
- **風險一律以「失敗次數／損失工時／帳單增量」計，不得以 MB 計**；
  swap 對 SSD 的損耗要換算成金額，與升規費用並列
- ⚠️ **輸出要寫成「遷就現況的權宜推薦」**，並明列本次診斷中**未能解決的行為問題** ——
  讓讀的人知道這台機器買的是什麼

## 邊界

**不適用**：伺服器／CI runner／共用推論機（多租戶，尖峰定義不同、成本多人攤提）；
記憶體可事後升級的機器（第三層的投資邏輯前提是「焊死、不可補救」）；
新入職或全新工作流（無歷史紀錄可掃，只能同儕類比並標暫定）。

**會給錯建議的四種情況**，各配一條補救：

| 情況 | 補救 |
|---|---|
| 偶發超大負載被 p90 平滑掉 | 改用「單次失敗代價 × 年度頻率」的期望損失，但須附歷史紀錄 |
| **瓶頸其實不在記憶體** | 第二層之前先過 **Step 4.5 的四項判定關卡**；不指向記憶體者本 skill 不受理 |
| 真實高並行需求被誤判為習慣 | 只憑活動時間分布判定，不憑主觀。有活動即不計為可削減 |
| 降載實驗偽陰性（任務集太簡單） | 任務集須取自近期真實任務且 ≥10 個，涵蓋主要工作型態 |

**可攜性**：指標的概念可攜，**自動量測不可攜** —— session 紀錄格式是 Claude Code 專有的，
其他 harness 走人工自陳版。要明講這個落差，不要讓人以為跑得出數字。

**隱私**：`scan_sessions.py` 只輸出統計量。跑在別人機器上時，
**不得輸出任何對話內容、程式碼或業務資訊**，這是硬要求。

**與其他 skill 的分界**：本 skill 診斷的是「人怎麼用 agentic 工具」，
不是服務端效能（那是 `datadog-setup-monitoring`、`seo-query` 的範圍），
也不是票務優先序（`priority-decision-tree-audit`）。

本 skill **不重寫**「壓縮率 ≠ 成本節省，以任務成功率＋端到端帳單為準」這條既有原則，
只引用它並延伸到記憶體軸（佔用量 ≠ 成本）。該原則若已寫在你的團隊規範裡，以那份為準。

## 注意事項

- **隱私是硬要求**：`scan_sessions.py` 與 `probe_host.sh` 只輸出統計量與設定結構。
  跑在別人機器上時，**不得輸出任何對話內容、程式碼或業務資訊**。
- **兩支腳本都是唯讀**，不修改設定、不刪除任何東西。第二層的動作多半不可逆 ——
  看到可疑的東西一律回報，由人決定；刪除前先用第二種方法確認對象真的可刪。
- **不改機器**：不得要求修改主機設定（保留期、日誌等）來累積資料。
  語料不足就聲明限制、限縮結論，判斷重心走當下現況。
- **量不到就寫 UNKNOWN**，不得寫 0。`0` 在本 skill 裡是有意義的行為訊號，
  用它代表「量不到」等於偽造旗標。
- **平台**：環境層只支援 macOS。其他平台走 `portability.md` 的人工自陳版，
  並在報告寫明環境層是盲區。

## 狀態說明

已被**兩台機器**套用過：裝置 A（重負載，v0.1 校準）與裝置 B（閒置型，v0.2）。
兩台的 profile 對照見 `portability.md`；哪些條文有實地事證、哪些還沒有，
分別記在 `behavior.md` 與 `environment.md` 各自的 `## 狀態說明` 表。

### 已完成的驗證

| 驗證 | 結果 |
|---|---|
| 第一層抓不抓得出已知為真的問題 | ✅ 裝置 A 跑出繞道率 96:1、103 個做過程式碼探勘的 session 只有 4 個用過索引、63.3% 從未派過 subagent、`cache_read` 佔 95.4% —— 與獨立稽核一致 |
| 回溯驗證：對一個已核准的真實個案跑第三層 | ✅ 仍判定「升規正當」（`R` = 3.1–3.4、`ρ` = 5.5、`σ` = 94%、`φ` = 0.6%、失敗證據 3 類、規格階梯已證否、共享替代有正當理由） |
| 不會變成死閘門 | ✅ 同一個案的缺口達 34 GB，即使行為層回收 8 GB，`R` 仍為 2.6 —— 判準不會用「再去優化」無限擋掉一個真實缺口 |
| **會不會誤判成升規案** | ✅ 裝置 B 走到「不受理」—— 四項判據全部指向運算瓶頸，本 skill 第一個不受理實例。**判準會擋掉不該進第三層的案子** |
| **跨裝置可攜性** | ⚠️ **部分驗證**。解析層有 35 個 fixture 回歸測試（CI 在 Linux 上跑）；環境層**無自動測試**，只支援 macOS。14 類已知失效見 `portability.md` |
| 門檻的跨人適用性 | ⚠️ **仍未驗證，且 v0.2 起在 `n < 20` 時不再輸出**。兩台不構成分布 |

⛔ 沒驗證過的放待累積，**不要憑空杜撰**。每次套用到新的人或新的機器，
回來更新那兩張表，並在 `portability.md` 的裝置 profile 加一列。
