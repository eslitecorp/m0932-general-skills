# agentic-workflow-diagnosis — agentic 工作環境盡職調查

## 核心理念

**這是盡職調查，不是採購把關。產出是給提案者的建議報告，不是准駁結論。**

「在資源有限的機器上擴大 agent 使用」的答案主要不在硬體，在**使用方法**。
所以本 skill 的主體是**從實際使用紀錄找出工作流程的行為不當，並給出可執行的調整方法**。
只有在行為與環境調整都已窮盡、提案者仍明確反映必要，才走到第三層 ——
而第三層產出的是**遷就一個本不該存在的現況的權宜推薦**，不是本 skill 的成就。

| 是 | 不是 |
|---|---|
| 診斷使用方法，給具體調整建議 | 訂一套更難通過的採購門檻 |
| 讀者是**提案者本人** | 讀者是簽核者 |
| 「你的探勘方式讓 context 膨脹了，改成這樣」 | 「你不符合升規資格」 |
| 非不得已不花錢了事 | 用預算解決行為問題 |

## 兩條軸，先選軸再選層

```text
第零層  可攜性前置 —— 這台量得到什麼         → portability.md   ← 兩軸都先做
   ↓
   ├─ 記憶體軸（主軸）「機器整體很慢／記憶體不夠／要不要升規」
   │     第一層  行為診斷 —— 使用方法對不對        → behavior.md    ← 主體
   │        ↓    改完 → 當場重量 → 仍不足才進下一層
   │     第二層  環境診斷 —— 有沒有純浪費與錯誤設定 → environment.md
   │        ↓    改完 → 當場重量 → 仍不足才進下一層
   │     第三層  缺口判定 —— 不得已的權宜推薦        → 見下方
   │
   └─ 干擾軸「開會／錄音／分享畫面的時候卡」        → interference.md
         窗內尾端量測 → 候選成因 → 當場重量
         ⛔ 預設不匯入第三層；查明是分頁停頓才轉記憶體軸提報
```

**先判軸，再判層。** 兩條軸問的是不同的問句：
記憶體軸問「這台的瓶頸是不是記憶體」，干擾軸問「並行工作是否讓一個即時任務掉格」。
⛔ 不要把干擾軸塞成 Step 4.5 的第五項判據 —— **一道閘門只保證它被設計去問的那個問題**，
拉伸它會讓記憶體軸開始受理它擋不住的案子。理由詳見 `interference.md`。

**每一層都要求「改完 → 複測 → 仍不足」才可進入下一層。**
這就是「非不得已不花錢了事」的機制實現，不必靠形容詞勸人。

### 複測 = 當場重量

**複測是分鐘級的，不是跨週累積。** 每一條建議都必須附「當場可驗的動作 + 立即重量指令」：

| 動作 | 當場重量 | 期望 |
|---|---|---|
| MCP 設定去重 → 重啟 | `pgrep -f <server> \| wc -l` | N → 1 |
| hook 去重 | 重開一個 session 看注入次數 | N → 1 |
| 探勘改走索引 | 重跑 `scan_sessions.py` 看 `index_use` | 0 → >0 |

⛔ **不得把「兩週後再跑一次比較」當成必要步驟**，也**不得要求修改主機設定來累積資料**
（`portability.md` 的 R2）。這樣申請模式可以在一次會談內走完。

⛔ **不要跳過第一層。** 第二層清的是垃圾與錯誤設定，清完機器會好一點，
但不會改變使用方法 —— 跳過第一層等於用打掃代替檢討。

## 工作流程

### Step 1｜判斷模式

| 使用者說的 | 軸／模式 | 做到哪裡 |
|---|---|---|
| 「agent 跑起來很卡」「我的工作流程哪裡有問題」 | 記憶體軸／**診斷模式** | 第一層 + 第二層的症狀對照表，30 分鐘內給建議。**不進申請流程** |
| 「要不要升規」「幫我評估硬體需求」 | 記憶體軸／**申請模式** | 三層走完，每層都要複測 |
| **「開會的時候跑 AI 會卡」「錄音／分享畫面會頓」** | **干擾軸** | 走 `interference.md`：窗內尾端量測 → 候選成因 → 當場重量。⛔ 不走記憶體軸三層 |

⛔ **「機器整體感覺慢」與「開會的時候卡」是兩件事，不要合併處理。**
後者有即時性截止時間，前者沒有 —— 量測方法、判準、收斂終點全都不同。
兩個都有的話兩軸都跑，但**分開報告**，不要把尾端值與穩態值放進同一張表。

### Step 1.5｜第零層：可攜性前置（每次都做，不可跳）

**必讀 `portability.md`**，然後：

```bash
python3 scripts/scan_sessions.py --preflight   # 語料側：量得到什麼
./scripts/probe_host.sh                        # 主機側：當下現況（macOS）
```

⛔ **不看 preflight 就直接讀指標，會把「量不到」讀成「量到 0」** ——
這兩件事在本 skill 裡的處置完全相反（`0` 是行為問題，`UNKNOWN` 不是）。

四個必看欄位：索引型 MCP 狀態、當前 session id 解不解得出、repo roots、語料有沒有被截斷。

### Step 2｜第一層：行為診斷（必做）

**必讀 `behavior.md`**，然後：

```bash
python3 scripts/scan_sessions.py
```

再補一次即時狀態（腳本不推算「還開著／未封存」）：用 `list_sessions` 取
`isRunning` / `isArchived` / `lastActivityAt`。

產出五個指標的實測值、命中的旗標、以及強度正規化後的值。
**樣本 `n < 20` 時不使用 p75／p90**，只用硬旗標與絕對值，並在報告寫明樣本量。

### Step 3｜給建議並要求當場重量

依槓桿大小排序，每條建議都要**可執行**且**附當場可跑的重量指令**。
**這一步不要一次給十條** —— 給最有槓桿的兩三條，重量後再談下一輪。

#### 建議的形狀（v0.3.1 起，三條硬規則）

1. ⛔ **不得要求大幅改變工作習慣。** 不同人、不同環境、不同工作情況 ——
   工作方式是前提不是待修的錯誤，**該優化的是它的實作成本**。
   「減少分頁」「換掉你的待辦方式」不是建議；
   「開啟某設定讓同樣的分頁少佔記憶體」才是。
   〔事證：使用者宣告「分頁即待辦佇列，逐頁解決，不可再減少」——
   而 Chrome 的 Memory Saver 保留全部分頁（佇列原樣）、只卸載閒置 renderer，
   habit 與成本本來就是兩層，判準先前把它們混在一起了〕
2. **給明確可執行的做法**，不給方向性的勸告。每條含：在哪裡操作、動什麼、
   當場重量指令、期望前→後。**允許即時查證網路上可靠的解決方案** ——
   查證結果要附來源，且⛔ **建議之前先查該方案在這台的現況**：
   已啟用的方案不能再當建議〔事證：Memory Saver 在該機已開
   （`high_efficiency_mode: state 2`），差一點被當成新建議提出〕。
3. **診斷是與人的迴圈，不是單向報告。** 收集 → 提案 → 人執行或補宣告 → 當場重量 →
   再收集，**直到資訊齊全才下最終結論**。⛔ 資訊沒收齊就出最終建議
   （含換機建議）是搶跑 —— 換機是「行為與環境的具體做法窮盡後仍不足」的結論，
   不是預設選項。

### Step 4｜第二層：環境診斷（第一層重量後仍不足才做）

**必讀 `environment.md`**。四層歸因、六個取數陷阱、症狀對照表都在那裡。

⛔ **進本層之前先過瓶頸歸因關卡**（見下方「不受理的判定」）。
歸因不指向記憶體的話，第二層的記憶體清查是白做的。

### Step 4.5｜不受理的判定（進第三層之前的關卡）

**第三層只處理記憶體軸。瓶頸不指向記憶體者不受理第三層** —— 這是邊界，不是推託。

⛔ **這道關卡只回答「瓶頸是不是記憶體」，不要拿它回答別的問句。**
即時性任務掉格（開會卡頓）走 `interference.md` 的干擾軸，有自己的收錄判準與收斂終點；
⛔ 不得在下表加第五項判據去涵蓋它。
判定用下面四項，**在不同負載時點各取一次，不得用單一快照**：

| # | 判據 | 指向記憶體 | 指向運算 |
|---|---|---|---|
| 1 | `Swapouts`（自開機累計） | > 0 且持續增加 | **= 0** → 洩壓閥從未開過 |
| 2 | `memory_pressure` 自報可用率 | 低 | **高** |
| 3 | `ps -ax` vs `pgrep -f .` 計數 | 差距大（`ps` 被截斷） | **一致** |
| 4 | 單一 process 瞬時 CPU（`top -l 2`） | 無特別高者 | **遠超 100%** |

四項一致指向運算 → **不受理，報告寫明並收在第二層**。
⛔ 此時升記憶體不會修好它；把降載實驗、共享替代、規格階梯套上去，是把證據放到錯的軸上。

四項互相矛盾 → 不要硬判，把四個值都列出來，說明無法歸因，並停在這裡。

〔事證：裝置 B 四項全部指向運算（`Swapouts` = 0 於 21 天 uptime、`memory_pressure` 77%、
772 vs 758 一致、單一非 agentic process 瞬時 246–326%），是本 skill 第一個不受理實例〕

### Step 5｜第三層：缺口判定（前兩層都窮盡，且提案者明確反映仍有必要）

**必讀 `audit-standard.md`。** 受理與否由那份的**四道閘門**決定，不由任何數值門檻決定：

```bash
python3 scripts/compute_gap.py --declaration <宣告.json> --measurement <量測.json>
```

⛔ **標準必須在量測之前 commit**（預先登記）。順序反過來的話，標準就是從想要的答案
回推出來的，審查者看得出來。`audit-standard.md` 第六節有程序。

⛔ **應然基線 = 宣告 ∩ 實測 L4**，不是「現值減掉浪費」。少了「人宣告了什麼」那一半，
L4 就無法否證（「我需要」→ L4 → 缺口成立）。

以下是那四道閘門的摘要，細節與各自的不受理條件以 `audit-standard.md` 為準：

| 閘門 | 問什麼 |
|---|---|
| G0 | 症狀落在記憶體軸（Step 4.5 四項判據，不同負載時點各取一次）|
| G1 | 前兩層窮盡（每條有前→後的實際數字；**L3 候選集**要跑完 A/B 四欄，缺一即不過）|
| G2 | 缺口實在（宣告 ∩ 實測 L4 非空；降載實驗有實測劣化）|
| G3 | 替代已證否（共享替代四理由之一；下一階規格不足；機型不可事後升級）|

- 缺口以**無因次比值**提報（`R` = 應然基線／實體容量、`ρ`、`σ`、`φ`），不寫死 GB。
  📌 `R` 沒有及格線 —— 它是提報用的量，受理與否由四道閘門決定
- **降載實驗（必做）**：刻意把佔用壓到容量以下，用 ≥10 個近期真實任務重跑。
  - 劣化 → 這就是「不升規會怎樣」的實測答案
  - 無劣化 → L4 分類錯誤，**退回第一層**
  - ⛔ 不得以「我覺得會很慢」代替
- **共享替代必答題**：能否由共用推論機／集中式服務滿足？
  理由須落在「資料落地限制／延遲不可容忍／離線可用性／供應商中斷降級」四者之一
- **規格階梯證否**：須證明「下一階較便宜的規格不足」，而非只證明本案規格夠
- **風險一律以「失敗次數／損失工時／帳單增量」計，不得以 MB 計**；
  swap 對 SSD 的損耗要換算成金額，與升規費用並列
- ⚠️ **輸出要寫成「遷就現況的權宜推薦」**，並明列本次診斷中**未能解決的行為問題** ——
  讓讀的人知道這台機器買的是什麼

## 產出格式

```markdown
# Agentic 工作環境診斷報告 — {對象}／{日期}

## 結論（三行內）
{使用方法的主要問題}｜{預估可回收}｜{是否需要升規}

## 〇、可攜性前置
{preflight 四欄：索引型 MCP 狀態／session id 來源／repo roots／語料有無截斷}
{量不到的項目逐一指名，標 UNKNOWN}
{其他 harness 的盲區與自陳答案，標為自陳}

## 一、行為診斷
{五個指標的實測值、強度正規化後的值、命中的旗標}
{樣本量；n < 20 時寫明未使用 p75／p90}

## 一之二、即時性干擾軸（僅在走干擾軸時出現）
{收錄判準兩條是否成立}
{客戶端結果指標，或標 UNKNOWN／自陳}
{idle 段 vs busy 段的尾端對照：p95 與 max、取樣頻率、取樣器自身成本}
{盲區逐項指名}

## 二、建議的調整（依槓桿大小排序）
1. {動作}｜預期效果 {量}｜**當場重量指令** {指令}｜期望 {前 → 後}

## 三、環境診斷（僅在第一層重量後仍不足時出現）
{瓶頸歸因四項判據}
{四層歸因表}

## 四、重量結果
{改完當場重跑的前後對照}

## 五、剩餘缺口與權宜推薦（僅在前兩層窮盡後出現）
{降載實驗結果、共享替代答案、規格階梯證否、**未能解決的行為問題**}
```

## 邊界

**不適用**：伺服器／CI runner／共用推論機（多租戶，尖峰定義不同、成本多人攤提）；
記憶體可事後升級的機器（第三層的投資邏輯前提是「焊死、不可補救」）；
新入職或全新工作流（無歷史紀錄可掃，只能同儕類比並標暫定）。

**會給錯建議的四種情況**，各配一條補救：

| 情況 | 補救 |
|---|---|
| 偶發超大負載被 p90 平滑掉 | 改用「單次失敗代價 × 年度頻率」的期望損失，但須附歷史紀錄 |
| **瓶頸其實不在記憶體** | 第二層之前先過 **Step 4.5 的四項判定關卡**；不指向記憶體者**第三層**不受理。若症狀是即時任務掉格，改走 `interference.md` 的干擾軸，不是不受理 |
| 真實高並行需求被誤判為習慣 | 只憑活動時間分布判定，不憑主觀。有活動即不計為可削減 |
| 降載實驗偽陰性（任務集太簡單） | 任務集須取自近期真實任務且 ≥10 個，涵蓋主要工作型態 |

**可攜性**：指標的概念可攜，**自動量測不可攜** —— session 紀錄格式是 Claude Code 專有的，
其他 harness 走人工自陳版。要明講這個落差，不要讓人以為跑得出數字。

**隱私**：`scan_sessions.py` 只輸出統計量。跑在別人機器上時，
**不得輸出任何對話內容、程式碼或業務資訊**，這是硬要求。

**與其他 skill 的分界**：本 skill 診斷的是「人怎麼用 agentic 工具」，
不是服務端效能（那是 `datadog-setup-monitoring`、`seo-query` 的範圍），
也不是票務優先序（`priority-decision-tree-audit`）。

本 skill **不重寫**「壓縮率 ≠ 成本節省，以任務成功率＋端到端帳單為準」這條既有原則，
只引用它並延伸到記憶體軸（佔用量 ≠ 成本）。該原則若已寫在你的團隊規範裡，以那份為準。

## 檔案清單

| 檔案 | 何時讀 |
|---|---|
| `portability.md` | **每次都讀**（換機器、換人都要先過前置檢查） |
| `behavior.md` | **每次都讀**（記憶體軸第一層是必做的） |
| `environment.md` | 記憶體軸第一層調整並重量後仍不足時 |
| `interference.md` | **使用者說的是「開會／錄音／分享畫面時卡」時讀**（干擾軸） |
| `audit-standard.md` | **走到第三層時必讀**。四道閘門、工作負載宣告模板、降載協議、預先登記程序、對外審查文件模板 |
| `scripts/scan_sessions.py` | 第零／第一層取數，直接執行 |
| `scripts/probe_host.sh` | 第零層的當下現況 probe（macOS） |
| `scripts/index-mcp-patterns.json` | 本機的索引型 MCP 不在預設清單裡時，加進去 |
| `scripts/probe_realtime.sh` | 干擾軸的窗內尾端取樣器（macOS，免 sudo，先自量成本） |
| `scripts/select_task_set.py` | 降載實驗的任務集選集器（規則化、決定性、只出統計量）。⛔ 一律帶 `--exclude-current` |
| `scripts/work-type-patterns.json` | 工作型態的工具名子字串擴充；⛔ 不要寫完整 server 名（A1） |
| `scripts/downclock_ballast.sh` | G2 降載實驗的壓艙物（macOS，免 sudo，唯讀）。⚠️ 只能把機器壓小，⛔ 模擬不了更大的機器 |
| `scripts/compute_gap.py` | 把四道閘門變成可執行的判定；同一份輸入只有一個結論 |
| `tests/` | 改動 `scan_sessions.py` 或 `compute_gap.py` 後必跑（101 個） |

## 注意事項

- **隱私是硬要求**：三支腳本只輸出統計量與設定結構。
  跑在別人機器上時，**不得輸出任何對話內容、程式碼或業務資訊**。
- **三支腳本都是唯讀**（`scan_sessions.py`／`probe_host.sh`／`probe_realtime.sh`），
  不修改設定、不刪除任何東西。第二層的動作多半不可逆 ——
  看到可疑的東西一律回報，由人決定；刪除前先用第二種方法確認對象真的可刪。
- **取樣器要先量自己**：`probe_realtime.sh` 開場空跑量自身成本。⛔ 這一步不可跳過 ——
  取樣器可以成為它要量的那個干擾源（實測 200.6 ms → 27.4 ms／次，差 7.3 倍）。
- **不改機器**：不得要求修改主機設定（保留期、日誌等）來累積資料。
  語料不足就聲明限制、限縮結論，判斷重心走當下現況。
- **量不到就寫 UNKNOWN**，不得寫 0。`0` 在本 skill 裡是有意義的行為訊號，
  用它代表「量不到」等於偽造旗標。
- **平台**：環境層只支援 macOS。其他平台走 `portability.md` 的人工自陳版，
  並在報告寫明環境層是盲區。
