# 審核標準：跨人跨裝置的第三層受理判準

**判斷依據**：任何走到第三層（硬體缺口）的案子，一律套本檔。
**套用方式**：本檔 + `scripts/compute_gap.py`，且**本檔的內容必須在量測之前 commit**。

> **這份標準的存在理由是它能說「不受理」。**
> 一個永遠說 yes 的標準沒有公信力。四道閘門每一道都寫出自己的不受理條件，
> 而且至少要有一台真實機器被它判過不受理 —— 這是可否證性的最低要求。

---

## 一、這份標準是什麼／不是什麼

| 是 | 不是 |
|---|---|
| 一份給提案者與審查者共用的受理判準 | 一套更難通過的採購門檻 |
| 問「你有沒有這一類證據」 | 問「你的數字超過多少」 |
| 人的需求與機的容量分開量，再取交集 | 拿機器現況當需求基準 |
| 跨人跨裝置可套，因為**證據的形狀**跨機器相同 | 跨人跨裝置可套，因為門檻被校準過（`n = 2`，校準不出來） |

⛔ 本檔不取代 `behavior.md`／`environment.md`。它是**第三層的受理判準**，
前兩層的診斷仍走那兩份；G1 就是在檢查那兩層有沒有真的走完。

---

## 二、為什麼沒有數字門檻

`portability.md` 的 C1 就在禁這件事：**門檻自引** ——
p75／p90 由正在被評判的同一份小樣本算出，卻印成「門檻」。
裝置 profile 目前 `n = 2`，**兩台不構成分布**，算不出跨裝置門檻。

所以本標準的所有門檻寫成**證據要求**：

> 每一道閘門問的不是「數字超過多少」，而是「**你有沒有這一類證據，以及它的形狀對不對**」。
> 證據的形狀跨機器相同（例如「降載實驗有實測劣化」），證據的值每台不同。
> **可攜性來自形式，不來自校準過的數值。**

⛔ 在 `n ≥ 20` 之前**不得**在本標準裡加入任何跨裝置數值門檻。
要加就是另一次預先登記，且要說明樣本從哪來。

📌 唯一允許的數值是**提案者自己宣告的值**（例如並行度上限、劣化的百分比門檻）——
那是宣告不是門檻，會被標成 `declared`，且會與實測對照。

---

## 三、兩份 profile：人與機分開

現行的 `應然基線 = 現值 − L1 − L2可削減 − L3未過A/B` **全部由機器現況推導**，
它從來沒問過「你的工作實際需要什麼」。這是循環的，也是 L4 無法否證的原因
（「我需要」→ L4 → 缺口成立）。標準把兩半拆開：

| | 內容 | 誰產出 | 何時 |
|---|---|---|---|
| **工作負載宣告（人）** | 並行度上限、宣告為不可壓縮的常駐項＋每項的觀察證據、劣化定義、機型可否事後升級 | **提案者本人** | 量測**之前**，且要 commit |
| **容量 profile（機）** | 實體記憶體、swap 配置、四層歸因後的實測值 | 量測 | 之後 |

### 應然基線 = 宣告 ∩ 實測 L4

```text
應然基線 = Σ( 項目 i : i ∈ 宣告的不可壓縮項  AND  i 實測落在 L4 )
R = 應然基線 / 實體容量
```

| 情況 | 處置 |
|---|---|
| 宣告了，實測也是 L4 | ✅ 計入應然基線 |
| 宣告了，但實測落在 L1／L2／L3 | ⛔ **不計入**。宣告不等於成立 |
| 宣告了，但說不出觀察證據 | ⛔ **不計入**。見下方宣告模板的硬要求 |
| 實測是 L4，但沒宣告 | ⛔ **不計入**。那是意外常駐，回 L1／L2 處理 |

**這個交集才是跨人可比的量** —— 它把「這個人的工作需要什麼」與
「這台機器實際擔了什麼」分開之後再取交集，兩邊都可以被否證。

⚠️ **per-session fork 的量由宣告的並行度決定，不由實測的並行度決定。**
實測 > 宣告 → 差額落 L2（可削減，回第一層）；實測 < 宣告 → 以宣告為上限計入，
但**必須有活動時間分布支撐**（`environment.md`：只憑活動分布判定，不憑主觀）。

## 四、四道閘門

**四道全過才受理。任一道不過就停在那裡並寫明停在哪 —— ⛔ 不得跳層。**

### G0｜軸線：症狀落在記憶體軸

- **要求的證據**：`SKILL.md` Step 4.5 的四項判據，**在不同負載時點各取一次**，不得單一快照。
  每一項都要標明方向：`memory` / `compute` / `inconclusive`
- **四種情況，窮盡且互斥**（⚠️ 這一段是第二次預先登記修訂的，見第十節）：

| # | 條件 | 判定 |
|---|---|---|
| 1 | 沒有任何判據指向記憶體，**且**至少一個取樣點四項全指向運算 | **不受理**（裝置 B 實例） |
| 2 | 同時有指向記憶體與指向運算的讀數 | **停住** —— 真正的矛盾，四個值全列出來說明無法歸因 |
| 3 | 沒有任何判據指向記憶體，**也**沒有任何取樣點四項全指向運算 | **停住** —— 全是 `inconclusive`，請在有負載的時點重取 |
| 4 | 有判據指向記憶體，且無指向運算的讀數 | **過** |

- 📌 情況 1 不要求「每一個取樣點都四項全 compute」。G0 問的是「瓶頸是不是記憶體」，
  **沒有任何一項指向記憶體時這個問題已經有答案了** —— 閒置時刻的 `inconclusive`
  不該把案子救回來。理由與修訂紀錄見第十節
- ⛔ 這道閘門只回答「瓶頸是不是記憶體」。即時任務掉格走 `interference.md` 的干擾軸，
  不在本標準範圍

### G1｜前兩層窮盡

- **要求的證據**：每一條都要有「**重量指令 + 前 → 後的實際數字**」
  - 第一層：`behavior.md` 給出的建議已套用並當場重量
  - 第二層 L1：清到零、**且修了成因**，重開機後複測仍為零
  - 第二層 L3：**A/B 四欄全部實測** —— 任務成功率／端到端完成時間／端到端帳單／常駐 footprint
- **不受理**：
  - 任一條只有宣稱、沒有前後值 → 不受理，退回該層
  - L3 的 A/B **缺任一欄** → 不受理。⛔ 不得用三欄推論，量不到就標 `UNKNOWN` 並讓本閘門不過
  - L1 只做了「手動清一次」沒修成因 → 不受理

### G2｜缺口實在

- **要求的證據**：
  - `R`／`ρ`／`σ`／`φ` 由 `compute_gap.py` 從**宣告 ∩ 實測 L4** 算出
  - **降載實驗**有實測劣化（協議見第五節）
- **不受理**：
  - 降載實驗**無劣化** → **L4 分類錯誤，退回第一層**
  - 宣告與實測 L4 的**交集為空** → 不受理
  - `σ` 為 `UNDEFINED`（swap 未配置）時，**不得**以 `σ` 支撐缺口；改以 `Swapouts` 為主判據
- 📌 `R` 沒有及格線。它是**提報用的量**，讓審查者看得到缺口的相對大小；
  受理與否由四道閘門決定，不由 `R` 的數值決定

### G3｜替代已證否

- **要求的證據**（兩項都要正面答覆，不得留空）：
  - **共享替代**：能否由共用推論機／集中式服務滿足？理由須落在
    「資料落地限制／延遲不可容忍／離線可用性／供應商中斷降級」**四者之一**
  - **規格階梯證否**：須證明「**下一階較便宜的規格不足**」，而非只證明本案規格夠
  - **機型可否事後升級**：可升級者**不走第三層**，走加購記憶體
- **不受理**：
  - 共享替代可行且不落在四理由之一 → 不受理
  - 只證明本案規格夠、未證明下一階不足 → 不受理
  - 機型可事後升級 → 不受理（走加購）

## 五、降載實驗協議（必須預先登記）

**目的**：回答「不升規會怎樣」。⛔ 不得以「我覺得會很慢」代替。

| 項目 | 規定 |
|---|---|
| **任務集** | ≥10 個**近期真實任務**，涵蓋主要工作型態。挑選規則必須預先登記；挑完的清單也要登記 |
| **降載方式** | 刻意把可用記憶體壓到宣告容量以下，壓法與壓到多少要登記 |
| **對照** | 同一組任務在正常條件下先跑一輪當基線 |
| **劣化定義** | **預先登記，事後不得改**。三種可選其一，登記在宣告裡 |
| **計分** | 每個任務逐一記錄，不只記總數。⛔ 不得只回報成功率百分比 |

### 劣化的三種定義（選一個，登記）

| 定義 | 判準 | 適用時機 |
|---|---|---|
| **A 任務成功率下降** | 任務能不能完成：OOM／process 被殺／工具呼叫失敗／需要重跑 | 預設。與 skill「風險以失敗次數／損失工時／帳單增量計」直接對齊 |
| B 完成時間超過基線 N% | `N` 須預先登記 | ⚠️ `n = 2` 下 `N` 沒有校準依據，只能是宣告值 |
| C 三項任一 | 成功率／時間／帳單任一惡化 | ⚠️ 門檻最寬，審查者最會質疑「三道門隨便一道就算過」 |

### 判讀

| 結果 | 處置 |
|---|---|
| 有劣化 | 這就是「不升規會怎樣」的實測答案 → G2 這一項通過 |
| **無劣化** | **L4 分類錯誤，退回第一層** ⛔ 不得解釋成「任務集不夠難」再重挑 |
| 任務集偽陰性的防範 | 挑選規則預先登記；⛔ 事後換任務集必須是新一次預先登記，舊的留在歷史上 |

## 六、預先登記程序

**沒有時間戳的檔案不算預先登記。**

1. 填好工作負載宣告（第八節模板），存成 JSON
2. 本檔、宣告、降載協議、以及「什麼算不受理」全部就位
3. **commit** —— commit hash 與時間戳就是登記憑證
4. 才開始量測

| 可以事後改的 | 不可以事後改的 |
|---|---|
| 補上量測值 | 閘門的定義與不受理條件 |
| 補上盲區與 `UNKNOWN` 的說明 | 劣化的定義 |
| 修正打錯的字 | 任務集的挑選規則 |

⛔ **不為了讓某台機器過閘門而調整閘門。** 真要改判準就是另一次預先登記，
且舊 commit 留在歷史上 —— 事後改得動內容，改不動歷史。

## 八、工作負載宣告模板（人）

存成 JSON 餵給 `compute_gap.py`。**每一項不可壓縮項都要附觀察證據，答不出來的不計入。**

```json
{
  "declared_by": "<角色或代號，不必真名>",
  "declared_at": "<YYYY-MM-DD>",
  "machine": {"model": "<機型>", "ram_gb": 16, "ram_upgradeable": false},
  "concurrency_declared": 5,
  "degradation_definition": "A_task_success_rate",
  "task_set_rule": "<挑選規則，例如：從近期 session 語料自動挑，涵蓋主要工作型態>",
  "incompressible": [
    {
      "name": "<項目>",
      "scales_with_concurrency": true,
      "claimed_mb": null,
      "observation": "<關掉它之後你怎麼觀察到成功率下降 —— 要具體到可查證的痕跡>",
      "shared_alternative_reason": "<資料落地限制｜延遲不可容忍｜離線可用性｜供應商中斷降級｜無>"
    }
  ]
}
```

**硬要求**：

- `observation` **不得**寫成「我需要它」「會很不方便」。要寫得出**可查證的痕跡** ——
  失敗紀錄、被殺的 process、重跑次數、工具呼叫錯誤。答不出來的項目
  `compute_gap.py` 會直接排除並在輸出裡指名
- `ram_upgradeable: true` → G3 直接不受理（走加購）
- `scales_with_concurrency: true` 的項目，計入量以 `concurrency_declared` 為上限

## 十、修訂紀錄

**每一次修訂都是一次新的預先登記。舊 commit 留在歷史上，這是刻意的** ——
審查者要看得到「改了什麼、什麼時候改、為什麼改」，而那三件事只有版本歷史證明得了。

### 修訂 1｜G0 的 `inconclusive` 處置（2026-09-03）

| | |
|---|---|
| **原規則** | 四項判據在**每一個**取樣點都一致指向運算 → 不受理 |
| **新規則** | 沒有任何判據指向記憶體，**且**至少一個取樣點四項全指向運算 → 不受理 |
| **前一版 commit** | `786aab0`（2026-09-03T18:18:28+08:00） |
| **觸發** | 標準第一次真的被套用 |

**發現的過程**：某台機器取了三個時點、12 個判據讀數，其中 **11 個指向運算、0 個指向記憶體**。
但取樣 3 落在閒置時刻（突發的 CPU 消耗者剛結束，`single_cpu` 因此標成 `inconclusive`），
所以「每一個取樣點都四項全 compute」不成立，已登記的邏輯輸出「無法歸因」。

**為什麼原規則錯了**：G0 問的是「瓶頸是不是記憶體」。
**沒有任何一項指向記憶體時，這個問題已經有答案了。**
閒置時刻的 `inconclusive` 代表「那一刻沒有瓶頸」，它不是反面證據，
不該把一個明確非記憶體的案子救回「無法判定」。
而且一台完全沒有瓶頸的機器當然不需要升規 —— 判它不受理是對的。

**為什麼這不是為了讓那台機器過關而裁剪**（三項可查證）：
