# 審核標準：跨人跨裝置的第三層受理判準

**判斷依據**：任何走到第三層（硬體缺口）的案子，一律套本檔。
**套用方式**：本檔 + `scripts/compute_gap.py`，且**本檔的內容必須在量測之前 commit**。

> **這份標準的存在理由是它能說「不受理」。**
> 一個永遠說 yes 的標準沒有公信力。四道閘門每一道都寫出自己的不受理條件，
> 而且至少要有一台真實機器被它判過不受理 —— 這是可否證性的最低要求。

---

## 一、這份標準是什麼／不是什麼

| 是 | 不是 |
|---|---|
| 一份給提案者與審查者共用的受理判準 | 一套更難通過的採購門檻 |
| 問「你有沒有這一類證據」 | 問「你的數字超過多少」 |
| 人的需求與機的容量分開量，再取交集 | 拿機器現況當需求基準 |
| 跨人跨裝置可套，因為**證據的形狀**跨機器相同 | 跨人跨裝置可套，因為門檻被校準過（`n = 2`，校準不出來） |

⛔ 本檔不取代 `behavior.md`／`environment.md`。它是**第三層的受理判準**，
前兩層的診斷仍走那兩份；G1 就是在檢查那兩層有沒有真的走完。

---

## 二、為什麼沒有數字門檻

`portability.md` 的 C1 就在禁這件事：**門檻自引** ——
p75／p90 由正在被評判的同一份小樣本算出，卻印成「門檻」。
裝置 profile 目前 `n = 2`，**兩台不構成分布**，算不出跨裝置門檻。

所以本標準的所有門檻寫成**證據要求**：

> 每一道閘門問的不是「數字超過多少」，而是「**你有沒有這一類證據，以及它的形狀對不對**」。
> 證據的形狀跨機器相同（例如「降載實驗有實測劣化」），證據的值每台不同。
> **可攜性來自形式，不來自校準過的數值。**

⛔ 在 `n ≥ 20` 之前**不得**在本標準裡加入任何跨裝置數值門檻。
要加就是另一次預先登記，且要說明樣本從哪來。

📌 唯一允許的數值是**提案者自己宣告的值**（例如並行度上限、劣化的百分比門檻）——
那是宣告不是門檻，會被標成 `declared`，且會與實測對照。

## 三、兩份 profile：人與機分開

現行的 `應然基線 = 現值 − L1 − L2可削減 − L3未過A/B` **全部由機器現況推導**，
它從來沒問過「你的工作實際需要什麼」。這是循環的，也是 L4 無法否證的原因
（「我需要」→ L4 → 缺口成立）。標準把兩半拆開：

| | 內容 | 誰產出 | 何時 |
|---|---|---|---|
| **工作負載宣告（人）** | 並行度上限、宣告為不可壓縮的常駐項＋每項的觀察證據、劣化定義、機型可否事後升級 | **提案者本人** | 量測**之前**，且要 commit |
| **容量 profile（機）** | 實體記憶體、swap 配置、四層歸因後的實測值 | 量測 | 之後 |

### 應然基線 = 宣告 ∩ 實測 L4

```text
應然基線 = Σ( 項目 i : i ∈ 宣告的不可壓縮項  AND  i 實測落在 L4 )
R = 應然基線 / 實體容量
```

| 情況 | 處置 |
|---|---|
| 宣告了，實測也是 L4 | ✅ 計入應然基線 |
| 宣告了，但實測落在 L1／L2／L3 | ⛔ **不計入**。宣告不等於成立 |
| 宣告了，但說不出觀察證據 | ⛔ **不計入**。見下方宣告模板的硬要求 |
| 實測是 L4，但沒宣告 | ⛔ **不計入**。那是意外常駐，回 L1／L2 處理 |

**這個交集才是跨人可比的量** —— 它把「這個人的工作需要什麼」與
「這台機器實際擔了什麼」分開之後再取交集，兩邊都可以被否證。

⚠️ **per-session fork 的量由宣告的並行度決定，不由實測的並行度決定。**
實測 > 宣告 → 差額落 L2（可削減，回第一層）；實測 < 宣告 → 以宣告為上限計入，
但**必須有活動時間分布支撐**（`environment.md`：只憑活動分布判定，不憑主觀）。

## 四、四道閘門

**四道全過才受理。任一道不過就停在那裡並寫明停在哪 —— ⛔ 不得跳層。**

### G0｜軸線：症狀落在記憶體軸

**問兩個獨立的問題，不是四項投票**：有沒有記憶體的正面證據？有沒有運算的正面證據？

⚠️ 這個結構是**第三次預先登記**改的（見 commit `ed07906`）。原本是四項判據各投一票，
但那四項的兩欄不對稱 —— 詳見修訂紀錄。

**證據取自當下現況（live probe），不回溯歷史紀錄**（R2）。
每一項由分析者標 `present` / `absent` / `unknown` 並附實測值，
**在不同負載時點各取一次**，不得單一快照。

| 記憶體的正面證據（任一 present 即成立） | 怎麼取 |
|---|---|
| `M1_swapouts_rising` | `Swapouts` > 0 且在觀測窗內增加 |
| `M2_ps_truncated` | `ps -ax` 計數顯著少於 `pgrep -f .` |
| `M3_compressor_absorbing` | 壓縮器在觀測窗內持續吸收，且 `φ` 極低 |
| `M4_pressure_low_falling` | `memory_pressure` 自報可用率低且下降 |

| 運算的正面證據（任一 present 即成立） | 怎麼取 |
|---|---|
| `C1_single_process_saturating` | 單一 process 瞬時 CPU 遠超 100%（`top -l 2` **第二次**採樣）|
| `C2_load_high_without_memory` | `λ` 高，且無任何記憶體證據 |

| 記憶體證據 | 運算證據 | 判定 |
|---|---|---|
| 有 | 無 | **過** |
| 無 | 有 | **不受理**（裝置 B 實例）|
| 有 | 有 | **停住** —— 真正的矛盾，值全列出來說明無法歸因 |
| 無 | 無 | **停住** —— 觀測窗內沒有成形的瓶頸，請在有負載時重取 |

⛔ **`absent` 不是反面證據。** 缺乏記憶體證據不等於運算的證據，反之亦然。
`unknown` 同樣不得被當成任一方的證據。這一條是修訂 2 的核心，有測試守著。

⛔ 這道閘門只回答「瓶頸是不是記憶體」。即時任務掉格走 `interference.md` 的干擾軸，
不在本標準範圍。

### G1｜前兩層窮盡

- **要求的證據**：每一條都要有「**重量指令 + 前 → 後的實際數字**」
  - 第一層：`behavior.md` 給出的建議已套用並當場重量
  - 第二層 L1：清到零、**且修了成因**，重開機後複測仍為零
  - 第二層 L3：**候選集全部跑過 A/B 四欄** —— 任務成功率／端到端完成時間／端到端帳單／常駐 footprint
- **L3 候選集怎麼定**（⚠️ 修訂 4 新增）：
  ```
  候選集 = {宣告項裡 non_resident_alternative ≠ 「無」的} ∪ {實測層別為 L3 的}
  ```
  每個宣告的不可壓縮項都**必須正面回答** `non_resident_alternative`：
  `遠端 API` / `http transport` / `原生執行` / `冷載入` / `無`。
  ⛔ 這一問不得省略 —— 省略它就能把項目直接放進 L4 而永遠不必面對 A/B。
  ⛔ **「我把它歸成 L4」不能讓它退出候選集。**
- **不受理**：
  - 任一條只有宣稱、沒有前後值 → 不受理，退回該層
  - L3 的 A/B **缺任一欄** → 不受理。⛔ 不得用三欄推論，量不到就標 `UNKNOWN` 並讓本閘門不過
  - **候選集沒跑完** → 不受理。⛔ 不得只測最好測的那一個
  - A/B 跑了但沒給 `alternative_disproved`（該替代到底有沒有被否證）→ 不算跑完
  - L1 只做了「手動清一次」沒修成因 → 不受理
- 📌 **基線也有牙齒**：有替代實作而該替代**未被 A/B 否證**的項目，
  一律不得計入應然基線（記為 L3 待驗）。否則 G1 不過但 `R` 仍虛報 ——
  「歸成 L4」在數字上依然有效。有測試守著

### G2｜缺口實在

- **要求的證據**：
  - `R`／`ρ`／`σ`／`φ` 由 `compute_gap.py` 從**宣告 ∩ 實測 L4** 算出
  - **降載實驗**有實測劣化（協議見第五節）
- **不受理**：
  - 降載實驗**無劣化** → **L4 分類錯誤，退回第一層**
  - 宣告與實測 L4 的**交集為空** → 不受理
  - `σ` 為 `UNDEFINED`（swap 未配置）時，**不得**以 `σ` 支撐缺口；改以 `Swapouts` 為主判據
- 📌 `R` 沒有及格線。它是**提報用的量**，讓審查者看得到缺口的相對大小；
  受理與否由四道閘門決定，不由 `R` 的數值決定

### G3｜替代已證否

- **要求的證據**（兩項都要正面答覆，不得留空）：
  - **共享替代**：能否由共用推論機／集中式服務滿足？理由須落在
    「資料落地限制／延遲不可容忍／離線可用性／供應商中斷降級」**四者之一**
  - **規格階梯**：兩種政策擇一，**都要在宣告時就選定**
    - `disproof`（嚴）：證明「下一階較便宜的規格不足」。
      ⚠️ **升級情境下這條結構上常常做不到** —— 見第五節的壓艙物限制
    - `declared_headroom`（寬）：以「覆蓋應然基線的那一階，再加一階」定機型。
      ⚠️ 比證否式寬鬆，**必須在審查文件寫明**。硬要求：
      **錨點是應然基線不是現值**（現值可能已含該被刪掉的浪費），有測試守著
  - **機型可否事後升級**：可升級者**不走第三層**，走加購記憶體
- **不受理**：
  - 共享替代可行且不落在四理由之一 → 不受理
  - 只證明本案規格夠、未證明下一階不足 → 不受理
  - 機型可事後升級 → 不受理（走加購）

## 五、降載實驗協議（必須預先登記）

**目的**：回答「不升規會怎樣」。⛔ 不得以「我覺得會很慢」代替。

### 🔴 壓艙物只能往下，不能往上

`downclock_ballast.sh` 只能把機器**壓小**，所以有一整類問題它結構上答不了：

| 你想證明 | 測得到嗎 |
|---|---|
| 現有規格不足 | ✅ 現況就在發生（換出速率、`Swapins`、失敗紀錄），甚至不需要壓艙物 |
| 某個宣告的 L4 項目其實可壓縮 | ✅ 把它關掉或收到宣告工作集，跑任務集 —— 這是降載實驗的本行 |
| **下一階規格不足** | ❌ **測不到。** 要在那一階的機器上跑，而手上沒有 |

**推論一**：G3 的 `disproof` 政策在**升級**情境下結構上常常做不到 ——
除非借得到候選規格的機器。這不是偷懶，是量測方向的限制。
`declared_headroom` 因此不只是「比較寬鬆的選項」，而是**升級情境下唯一做得到的那個**。
⚠️ 但寬鬆是真的，審查文件要寫明。

**推論二**：降載實驗**問的不是「多大的機器才夠」**（測不到），
而是「**這些宣告為不可壓縮的東西，真的不可壓縮嗎**」—— 逐項降載、跑任務集、看劣化。
這個問題壓艙物答得了，而且答案會直接改寫應然基線。

### 兩種降載形態，⛔ 不要預設是第一種

| 形態 | 做法 | 適用 |
|---|---|---|
| **整項移除** | 把宣告的不可壓縮項關掉，跑任務集 | 該項**真的可以關**時 |
| **工作集縮減** | 把該項收到宣告的工作集大小，跑任務集 | 該項**不可能整項關掉**時（瀏覽器、作業系統、公司強制的資安代理…） |

⛔ **「整項關不掉」不等於「這一項驗不了」。** 第一次為真實機器設計降載實驗時，
瀏覽器那一項被寫成「關掉 Chrome 跑任務集」—— 而使用者的前提是**瀏覽器不可能關掉**。
那不是使用者不配合，是**實驗形態選錯了**：對一個不可能歸零的項目，
可驗的問題不是「沒有它行不行」，而是「**要多少才夠**」。

工作集縮減的實驗要同時回報**固定成本**（收到最小仍然存在的那一段）——
它決定了這一項的下界，也決定了縮減的報酬什麼時候見底。
〔事證：某機的瀏覽器固定成本（主 process／GPU／Utility）1,575 MB 與分頁數無關；
可縮的 9,169 MB 分佈在 40 個 renderer，最重的 1 個就佔 12.3%。
從 40 收到 10 省 4,293 MB，從 10 再收到 5 只多省 1,787 MB —— 報酬遞減〕

📌 **縮減量與規格階梯的關係要畫成表交給提案者選**，不要替他決定。
判準能算出「收到 N 以下會掉一階」，但**收到 N 是不是還能工作，只有他知道**。

| 項目 | 規定 |
|---|---|
| **任務集** | `scripts/select_task_set.py --n 10 --days 30 --exclude-current --json > downclock-task-set.json`。規則化、決定性（重跑必得同一份），只輸出 session id／工具名／計數／時間。⛔ 不足 n 個時**不得放寬 `--days` 或降低 `--n` 來湊數** —— 那會把規則化挑選變成挑符合條件的樣本 |
| **降載方式** | `scripts/downclock_ballast.sh --ceiling <GB> --confirm`。壓法與**實際配置到的量**要登記（配置量可能小於目標，腳本會印出來） |
| **對照** | 同一組任務在正常條件下先跑一輪當基線 |
| **劣化定義** | **預先登記，事後不得改**。三種可選其一，登記在宣告裡 |
| **計分** | 每個任務逐一記錄，不只記總數。⛔ 不得只回報成功率百分比 |

### ⛔ 劣化定義必須能捕捉被測項目的代價

**選定義之前先問：這個定義量得到每一個宣告項的代價嗎？**

〔事證：某機宣告「瀏覽器分頁即待辦佇列，逐頁解決中」。
那一項既無可縮減量（工作集＝當下現況），而**關掉分頁的代價是工作佇列遺失** ——
不會有任何任務失敗。已登記的劣化定義 A（任務成功率）**量不到那種代價**，
於是那一項在 G2 底下不可驗，而它佔基線 50.9%〕

處置：宣告項可帶 `g2_unvalidatable: {"reason": "..."}`。
`compute_gap.py` 會**指名它、算出它佔基線的百分比、並讓 G2 停住**。

⛔ **不可驗不等於已驗證。** 停在這裡由審查者決定：
接受一個未驗證的宣告，或改用能捕捉該項代價的劣化定義 —— 後者是**新一次預先登記**。

📌 這件事要在挑劣化定義時就想，不是走到 G2 才發現。
定義 A 適合「關掉會讓事情做不完」的項目；
「關掉會讓事情**找不到**」「關掉會**丟掉狀態**」這兩類，A 都看不見。

### 劣化的三種定義（選一個，登記）

| 定義 | 判準 | 適用時機 |
|---|---|---|
| **A 任務成功率下降** | 任務能不能完成：OOM／process 被殺／工具呼叫失敗／需要重跑 | 預設。與 skill「風險以失敗次數／損失工時／帳單增量計」直接對齊 |
| B 完成時間超過基線 N% | `N` 須預先登記 | ⚠️ `n = 2` 下 `N` 沒有校準依據，只能是宣告值 |
| C 三項任一 | 成功率／時間／帳單任一惡化 | ⚠️ 門檻最寬，審查者最會質疑「三道門隨便一道就算過」 |

### 判讀

| 結果 | 處置 |
|---|---|
| 有劣化 | 這就是「不升規會怎樣」的實測答案 → G2 這一項通過 |
| **無劣化** | **L4 分類錯誤，退回第一層** ⛔ 不得解釋成「任務集不夠難」再重挑 |
| 任務集偽陰性的防範 | 挑選規則預先登記；⛔ 事後換任務集必須是新一次預先登記，舊的留在歷史上 |

## 六、預先登記程序

**沒有時間戳的檔案不算預先登記。**

1. 填好工作負載宣告（第八節模板），存成 JSON
2. 本檔、宣告、降載協議、以及「什麼算不受理」全部就位
3. **commit** —— commit hash 與時間戳就是登記憑證
4. 才開始量測

| 可以事後改的 | 不可以事後改的 |
|---|---|
| 補上量測值 | 閘門的定義與不受理條件 |
| 補上盲區與 `UNKNOWN` 的說明 | 劣化的定義 |
| 修正打錯的字 | 任務集的挑選規則 |

⛔ **不為了讓某台機器過閘門而調整閘門。** 真要改判準就是另一次預先登記，
且舊 commit 留在歷史上 —— 事後改得動內容，改不動歷史。

## 七、對外審查文件模板

給會質疑的審查者看的。**「什麼結果會讓結論反過來」是必填欄位** ——
答不出來的判準不是判準。


## 八、工作負載宣告模板（人）

存成 JSON 餵給 `compute_gap.py`。**每一項不可壓縮項都要附觀察證據，答不出來的不計入。**

```json
{
  "declared_by": "<角色或代號，不必真名>",
  "declared_at": "<YYYY-MM-DD>",
  "machine": {"model": "<機型>", "ram_gb": 16, "ram_upgradeable": false},
  "concurrency_declared": 5,
  "degradation_definition": "A_task_success_rate",
  "task_set_rule": "<挑選規則，例如：從近期 session 語料自動挑，涵蓋主要工作型態>",
  "incompressible": [
    {
      "name": "<項目>",
      "scales_with_concurrency": true,
      "claimed_mb": null,
      "observation": "<關掉它之後你怎麼觀察到成功率下降 —— 要具體到可查證的痕跡>",
      "shared_alternative_reason": "<資料落地限制｜延遲不可容忍｜離線可用性｜供應商中斷降級｜無>"
    }
  ]
}
```

**硬要求**：

- `observation` **不得**寫成「我需要它」「會很不方便」。要寫得出**可查證的證據**。
  兩種都算（⚠️ 由 commit `ed07906` 放寬）：
  - **當下使用證據（優先）**：這個東西**現在正在被用**，且有可數的活動 ——
    模型已載入並有查詢、MCP 有呼叫次數、容器有 1:1 活著的 client、process 有 CPU 活動。
    這與 R2「當下現況優先」一致；原本只收歷史痕跡的寫法其實與 R2 矛盾
  - **歷史痕跡**：失敗紀錄、被殺的 process、重跑次數、工具呼叫錯誤
- 📌 **當下有在用 ≠ 不可壓縮。** 使用證據只讓它進入候選集（計入基線的候選），
  **它是不是 L4 最終由 G2 的降載實驗決定**。⛔ 不得用「現在有在用」代替降載實驗
- 答不出來的項目 `compute_gap.py` 會直接排除並在輸出裡指名
- `ram_upgradeable: true` → G3 直接不受理（走加購）
- `scales_with_concurrency: true` 的項目，計入量以 `concurrency_declared` 為上限

## 八之二、寫判準時的六條教訓

**這一節的讀者是「改判準的人」，不是套用判準的分析者。** 六條都來自這份標準自己被改的
過程 —— 每一條都對應一次真的踩到的漏洞，發現過程在 commit 裡（見第十節的查法）。

1. ⛔ **判準出現「一致」「全部」這類量詞時，同時規定第三種值怎麼算。**
   只想過兩種值，程式碼會替你決定第三種，而那個決定沒有被任何人審過。
2. ⛔ **每一欄都要問「這個值有鑑別力嗎」** —— 即「處在其他狀態時，這一欄會不會長得一樣」。
   答案是「會」的話，那一欄不是判據；把它寫成判據就是**製造訊號**。
3. ⛔ **判準之間會互相矛盾，寫的時候要橫向對照。**
   〔例：要求提案者拿出歷史證據，與 R2「不改機器去累積資料」是同一件事的兩面〕
4. ⛔ **要求「每一項都要有 X」時，同時規定「哪些項算在內」。**
   前者是列的完整性，後者是**集合的完整性** —— 只寫前者，分析者可以靠縮小集合過關。
5. ⛔ **閘門不過的同時，數字也要跟著修正。**
   只擋住結論、不修正 `R`，審查者看到的仍是虛報的缺口。判準與提報量要一起改。
6. ⛔ **寫下一個實驗協議之前，先問「這個實驗在物理上做得到嗎」。**
   條文的嚴謹度不等於可執行性。更一般地：**驗證的本質是「拿掉它的代價有指名的證據」，
   實驗只是取得證據的方法之一** —— 把「驗證」與「某一種實驗」劃等號，會撞牆三次。

## 十、修訂歷史

判準的每一次修訂都是一次新的預先登記，**紀錄在 commit，不在本檔** ——
commit hash 與時間戳是登記憑證：事後改得動檔案，改不動歷史。

```bash
git log --grep='預先登記' -- agentic-workflow-diagnosis/   # 全部登記（13 則）
git log --grep='申請方'   -- agentic-workflow-diagnosis/   # 方向揭露（§七 必填欄位的來源）
```

每一則 commit 訊息含：**方向**（有利／不利於申請方）、發現的過程、改了什麼、留下的教訓。
判準本身該記的教訓已經收進第八之二節。

⛔ **不要在本檔重建一份修訂摘要。** 同一段歷史有兩個載體時必然各自演化，
而生效的是被讀到的那一份 —— 本檔可事後編輯，commit 不行，所以正本在 commit。
